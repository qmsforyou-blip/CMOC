## 3. Независимое подтверждение identity

Независимые материалы описывают Reverse PFMEA не просто как обычный audit и не просто как PFMEA review за столом.

Устойчиво повторяется следующая конструкция:

**PFMEA model → actual station/process → review/test controls → discover gaps/new failure modes → action → update/improve PFMEA/process.**

Это существенно совпадает с рабочей CMOC-гипотезой:

**MODEL → FIELD → OBSERVATION / VERIFICATION → GAP / NEW FAILURE MODE → ACTION → VERIFY → REASSESS → MODEL UPDATE.**

При этом отдельные источники различаются в деталях: одни акцентируют RPN reduction, другие — control effectiveness, третьи — continuous improvement и обновление PFMEA. Эти различия не разрушают общую структуру.

## 4. Boundary check: Audit

Reverse PFMEA не следует поглощать существующей машиной Audit.

### Audit
Общая логика:

**CRITERION → CHECK → EVIDENCE → CONFORM / NONCONFORM → ACTION**

### Reverse PFMEA
Специализированная логика:

**PFMEA FAILURE MODE → EXPECTED CONTROL → ACTUAL STATION → CONTROL EXISTENCE → CONTROL EFFECTIVENESS → NEW FAILURE MODE CHALLENGE → ACTION → PFMEA FEEDBACK**

Отличительные признаки Reverse PFMEA:

1. критерием является не только внешний стандарт, а конкретная модель failure modes/control architecture;
2. проверяется не только наличие документа/контрмеры, но её работа в реальном процессе;
3. допускается намеренное создание/провокация failure mode для проверки robustness;
4. результатом является изменение не только локального действия, но и самой risk model — PFMEA;
5. Reverse PFMEA предназначен для proactive risk reduction, а не только для проверки соответствия.

**Boundary verdict:** Reverse PFMEA = специализированная Machine, использующая Audit/Verification как внутренние механизмы.

## 5. Boundary check: PFMEA Review

Обычный PFMEA Review отвечает на вопрос:

> насколько актуальна и адекватна модель риска?

Reverse PFMEA отвечает на более узкий и операционный вопрос:

> соответствует ли реальный процесс этой модели риска и действительно ли предусмотренные controls работают?

Поэтому Reverse PFMEA является не просто другим названием PFMEA Review.

## 6. Boundary check: Problem Solving

Problem Solving начинается от обнаруженного quality problem и ищет cause / systemic cause / corrective action.

Reverse PFMEA может выполняться без фактически произошедшего дефекта. Его исходной точкой может быть scheduled proactive review.

Поэтому:

- **Problem Solving:** PROBLEM → CAUSE → CORRECTIVE ACTION → EFFECTIVENESS
- **Reverse PFMEA:** RISK MODEL → FIELD VERIFICATION → CONTROL GAP / NEW FAILURE MODE → RISK REDUCTION

Они могут соединяться, но не являются одной Machine.

## 7. Boundary check: LPA / Layered Audit

LPA проверяет выполнение заранее заданных критериев на уровне процесса/слоя управления.

Reverse PFMEA может использовать LPA как источник данных, но имеет собственную специализированную модель проверки:

**Failure Mode → Prevention/Detection Control → Effectiveness → New Failure Mode challenge → PFMEA feedback.**

Следовательно, Reverse PFMEA не является новым названием LPA.

## 8. Machine identity

### Candidate identity

**Reverse PFMEA** — специализированная диагностико-верификационная Machine, которая сопоставляет актуальную PFMEA-модель failure modes с фактическим состоянием конкретной производственной станции/процесса, проверяет существование и эффективность prevention/detection controls, ищет новые failure modes и возвращает результаты в risk model и action system.

### Input

- current PFMEA;
- failure modes;
- station/process;
- control methods;
- audit criteria/checklist;
- schedule;
- cross-functional team;
- фактические данные процесса.

### Core action

1. выбрать запланированную станцию;
2. собрать cross-functional team;
3. взять PFMEA и checklist;
4. пройти failure modes;
5. проверить наличие controls;
6. проверить их фактическую работоспособность;
7. challenge process для обнаружения новых failure modes;
8. зафиксировать gaps / findings;
9. сформировать action plan;
10. feed back results into PFMEA / risk assessment / process improvement.

### Output

- verified controls;
- control gaps;
- new potential failure modes;
- actual evidence;
- action plan;
- основания для изменения Occurrence/Detection;
- обновлённая risk model.

## 10. Important architectural distinction

Reverse PFMEA не следует канонизировать как универсальную Machine управления риском.

Его сильная сторона — **специализированная связь между risk model и реальным процессом**.

Рабочая формула:

**RISK MODEL → REAL PROCESS → CONTROL VERIFICATION → FAILURE MODE CHALLENGE → GAP / NEW FM → ACTION → REASSESS → MODEL UPDATE**

Это позволяет рассматривать Reverse PFMEA как одну из реализаций более общего CMOC-паттерна согласования модели управления с фактическим состоянием объекта.

## 11. Relation to Risk Model Feedback Loop

Independent cross-check поддерживает гипотезу, что за GM Risk Reduction стоит более общий паттерн:

**MODEL → FIELD → EVIDENCE → GAP → ACTION → VERIFY → MODEL UPDATE**

Но Reverse PFMEA и этот Pattern не следует смешивать:

- **Risk Model Feedback Loop** — потенциальный reusable Pattern;
- **Reverse PFMEA** — специализированная Machine, реализующая этот Pattern в области process-risk / PFMEA.

Pattern остаётся отдельным объектом для следующего cross-check.
