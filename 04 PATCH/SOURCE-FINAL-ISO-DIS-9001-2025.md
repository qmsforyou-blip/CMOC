# 2. ГЛАВНЫЙ РЕЗУЛЬТАТ ИСТОЧНИКА

ISO дал CMOC не готовую онтологию и не каталог организационных механизмов, а набор повторяющихся архитектурных конструкций, через которые может быть описана управляемая организационная система.

Наиболее сильная рабочая конструкция:

```text
REQUIREMENT
      ↓
REALIZATION
      ↓
RESULT
      ↓
EVIDENCE
      ↓
STATE / EVALUATION
      ↓
DECISION
      ↓
ACTION
      ↓
CHANGE
      ↓
NEW RESULT
```

Эта схема является **CMOC cross-clause candidate**, а не Source Claim одного пункта и не каноническим элементом CORE.

# 3. SYSTEM

Одна из устойчивых конструкций источника:

```text
PURPOSE / CONTEXT
        ↓
REQUIREMENTS
        ↓
SYSTEM OF PROCESSES
        ↓
CONTROLLED REALIZATION
        ↓
RESULTS
```

При этом:

```text
SYSTEM
≠
SET OF ISOLATED PROCESSES
```

Процессы рассматриваются во взаимодействии и взаимозависимости.

**Ключевое различение:**

```text
PROCESS
≠
SYSTEM OF INTERACTING PROCESSES
```

**Статус:** STRONG WORKING CANDIDATE.

# 4. PROCESS

Устойчивая процессная конструкция:

```text

 ↓
ACTIVITIES
 ↓

 ↓
RECEIVER
```

и одновременно:

```text
PROCESS
 ↔

```

Следовательно:

> Управление отдельным процессом и управление системой взаимодействующих процессов — различные задачи.

**Статус:** CANDIDATE / MULTI-CONFIRMATION.

# 9. EVIDENCE

Повторяющаяся информационная конструкция:

```text
ACTIVITY
 ↓
RESULT
 ↓
EVIDENCE
 ↓
DOCUMENTED INFORMATION
```

Evidence относится, в частности, к conformity, release, audit, management review, corrective action и другим результатам, где Source устанавливает соответствующее требование.

### Ключевое различение

```text
RESULT
≠
EVIDENCE OF RESULT
```

**Статус:** STRONG CANDIDATE / MULTI-CONFIRMATION.

# 10. DOCUMENT — DOCUMENTED INFORMATION — RECORD

ISO-028 дал наиболее сильную добычу в этой области.

Функциональная схема Source:

```text
DOCUMENTED INFORMATION
        │
        ├── DOCUMENTATION
        │
        └── RECORDS
```

При этом:

```text
DOCUMENTATION
→ information created for operation

RECORD
→ evidence of results achieved
```

Но эта схема **не канонизируется как CMOC ontology**.

### Критическое различение

```text
DOCUMENT
≠
DOCUMENTED INFORMATION
≠
RECORD
```

Дополнительное различение:

```text
DOCUMENTED INFORMATION
≠
KNOWLEDGE
```

Source допускает organizational knowledge, не обязательно представленное в форме documented information.

### Дополнительные выводы

Documented information является не просто «документом», а информацией вместе с носителем, подлежащей управлению в течение жизненного цикла.

```text
NEED
 ↓
CREATE / UPDATE
 ↓
IDENTIFY / DESCRIBE
 ↓
REVIEW / APPROVE
 ↓
ACCESS / USE
 ↓
PRESERVE
 ↓
CHANGE CONTROL
 ↓
RETENTION / DISPOSITION
```

**Статус:** STRONG CANDIDATE / MULTI-CONFIRMATION.

# 11. KNOWLEDGE

Сильная конструкция источника:

```text
PROCESS / CONFORMITY NEED
        ↓
KNOWLEDGE NECESSARY
        ↓
MAINTAIN
        ↓
MAKE AVAILABLE
```

И динамический контур:

```text
CHANGING NEEDS / TRENDS
        ↓
CURRENT KNOWLEDGE
        ↓
KNOWLEDGE GAP
        ↓
ACQUIRE / ACCESS
        ↓
ADDITIONAL KNOWLEDGE / UPDATE
```

### CMOC interpretation

> Достаточность знания определяется относительно функции, процесса и изменяющейся потребности, а не просто наличием некоторого массива знаний.

**Статус:** STRONG WORKING CANDIDATE.

# 12. ROLE / ACCOUNTABILITY

ISO-013 и связанные clauses дают конструкцию:

```text
TOP MANAGEMENT
 ↓
ACCOUNTABILITY
 ↓
RELEVANT ROLES
 ↓
RESPONSIBILITY + AUTHORITY
 ↓
ACTIONS / REPORTING
 ↓
RESULTS
```

Ключевое различение:

```text
RESPONSIBILITY
≠
ACCOUNTABILITY
```

Responsibility за activity может быть распределена или делегирована; accountability за результат в установленном Source контексте не сводится к делегированной responsibility.

Для QMS effectiveness Source связывает accountability с top management.

**Статус:** STRONG CANDIDATE / MULTI-CONFIRMATION.

# 13. PEOPLE / FUNCTION / TECHNOLOGY

ISO-020 дал отдельную важную конструкцию:

```text

        ↓
REQUIRED CAPABILITY
        ↓
PEOPLE
        OR
TECHNOLOGICAL REALIZATION
        ↓
PROCESS OPERATION / CONTROL
        ↓
QMS RESULT
```

При этом required workforce определяется не только headcount, но также workload, number и organizational knowledge.

### Ключевые различения

```text
PEOPLE AS RESOURCE
≠
PEOPLE AS HEADCOUNT
```

```text
REQUIRED PEOPLE
≠
FIXED STAFF
```

```text
PEOPLE
≠
IRREPLACEABLE MEANS OF FUNCTION
```

Технологическая замена человека требует оценки risks, opportunities, ethical behaviour и accountability.

**Статус:** CANDIDATE / SINGLE-SOURCE.

### Output-level

```text

 ↓

```

### System-level

```text

 ↓
CAUSE
 ↓
CORRECTIVE ACTION
 ↓
EFFECTIVENESS REVIEW
 ↓

```

### Ключевые различения

```text

≠

≠

```

Также corrective action не требуется автоматически для каждой nonconformity: Source связывает её необходимость с оценкой причин, последствий, повторяемости и другими условиями.

# 21. MACHINE-РЕЗУЛЬТАТ ISO

ISO дал большое количество mechanisms:

```text
M
├── Process management
├── PDCA
├── Context determination
├── Risk / opportunity action
├── Requirement review
├── Design control
├── Operational control
├── Release control
├── Nonconforming-output control
├── Performance evaluation
├── Internal audit
├── Management review
├── Corrective action
└── Continual improvement
```

Но принципиальное различение сохраняется:

```text
MECHANISM
≠
MACHINE
```

Источник часто описывает управленческую последовательность, но не задаёт конкретную воспроизводимую организационную или физическую реализацию.

Поэтому Machine Candidates не переносились автоматически в MACHINE-CATALOG.

### Итог

> ISO является богатым источником Mechanisms, но значительно более слабым источником готовых CMOC Machines.

# 22. ЧТО ИСТОЧНИК НЕ ПОДТВЕРДИЛ

ISO не дал достаточных оснований для:

- готового универсального Machine Catalog;
- универсальной физической реализации Machine;
- универсальной Role-Chain;
- отождествления Mechanism и Machine;
- отождествления documented information и record;
- отождествления evaluation и decision;
- единой канонической цепочки всех clauses;
- универсальной ontology организации.

Поэтому эти конструкции **не канонизируются**.

# 23. САМЫЕ СИЛЬНЫЕ КАНДИДАТЫ ДЛЯ MULTI-CONFIRMATION

Следующие десять узлов рекомендуется проверять в следующих независимых источниках:

1. **Requirement → realization → result**
2. **Result → evidence**
3. **State → permitted action**
4. **Evidence → evaluation**
5. **Analysis ≠ evaluation**
6. **Evaluation → opportunity / need**
7. **Information → review → decision / action**
8. **Reaction ≠ correction ≠ corrective action**
9. **Responsibility ≠ accountability**
10. **Documented information ≠ knowledge ≠ record**

Если независимые источники подтвердят эти конструкции, они могут перейти из candidate layer в более устойчивый слой CMOC.

# 24. ФИНАЛЬНЫЙ АРХИТЕКТУРНЫЙ ВЫВОД

Главный результат ISO для CMOC можно сформулировать так:

> **ISO не содержит готового CMOC. Он содержит большое количество повторяющихся управленческих различений, отношений и механизмов, из которых может быть реконструирована более общая архитектура управляемой организации.**

Именно поэтому источник ценен не как перечень требований ISO, а как независимое поле подтверждения архитектурных гипотез CMOC.

Фундаментальная рабочая гипотеза после закрытия источника:

```text
REQUIREMENT
      ↓
CONTROLLED REALIZATION
      ↓
RESULT
      ↓
EVIDENCE
      ↓
EVALUATION OF STATE / PERFORMANCE
      ↓
OPPORTUNITY / NEED
      ↓
DECISION / ACTION
      ↓
CHANGE
      ↓
NEW STATE
```

**Статус:** STRONG CMOC CROSS-CLAUSE CANDIDATE.

**Не канонизировать.**
