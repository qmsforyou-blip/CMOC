## 1. Основание изменения

После версии STD-008 v0.1 выполнен расширенный последовательный тест на источнике:

`Архитектура управляемости. Книга 1. Требования и реальность`

Производственная цепочка:

`SOURCE → EXTRACTION → DISTINCTIONS → FORMULATIONS → NOMENCLATURE → CLASSIFICATION → PASSPORT → RELATIONS → CANONIZATION`

Проверены:

- M02: 40 Extraction Records → 40 Distinction Records;
- M03: 40 Distinctions → 120 Formulations;
- M04: 120 Formulations → 36 Nomenclature Candidates;
- M05: 36 Nomenclature Candidates → 36 Classification Records;
- M06: 36 Classification Records → 36 Passport Records;
- M07: 36 Passports → 18 Relation Candidates;
- M08: 36 Passport Records + 18 Relation Candidates → решения канонизации.

Дополнительно проверены reverse trace и negative test на зависимости объекта от основания.

## 2. Что подтверждено тестом

### 2.1. Передача между модулями

Результат одного модуля может служить входом следующего без обязательного повторного чтения исходного источника.

Норма:

`OUTPUT[n] → INPUT[n+1]`

Возврат к SOURCE является исключением для спора, ошибки, уточнения, аудита или дефицита основания.

### 2.2. Сквозная прослеживаемость

Минимальная производственная цепочка подтверждена:

`SOURCE_ID → BATCH_ID → EXTRACTION_RECORD_ID → DISTINCTION_ID → FORMULATION_ID → NOMENCLATURE_ID → CLASSIFICATION_ID → PASSPORT_ID → RELATION_ID → CANON_ID`

При этом не каждый объект обязан иметь все последующие звенья: производство может корректно завершаться статусом `PROVISIONAL` или `NEEDS_EVIDENCE`.

### 2.3. Обратная трассировка

Для производного объекта должна быть возможна обратная навигация к его основанию.

Минимум:

`OBJECT → SOURCE`

Полная форма:

`OBJECT → предшествующие производственные записи → EXTRACTION → SOURCE`

Для критичных объектов требуется dependency-aware trace:

`OBJECT ← конкретные основания`

### 2.4. Потеря основания должна менять степень уверенности

Negative test подтвердил правило:

> Удаление существенного основания не может оставить неизменным уровень уверенности в производном объекте.

Возможный переход:

`CANONICAL → PROVISIONAL → NEEDS_EVIDENCE`

или иной эквивалентный пересмотр статуса.

### 2.5. Семантические границы удерживаются

Тест подтвердил необходимость следующих инвариантов:

- `SOURCE ≠ REPRESENTATION`
- `TERM OCCURRENCE ≠ TERM ENTITY`
- `SAME TERM ≠ SAME ENTITY`
- `TYPE ≠ CANONICAL OBJECT`
- `RELATION CANDIDATE ≠ ESTABLISHED RELATION`
- `PASSPORT ≠ INVENTION`
- `ABSENCE OF EVIDENCE ≠ EVIDENCE`
- `ACTIVITY ≠ MANAGEMENT`
- `FORMAL PROCESS ≠ MANAGEMENT ARCHITECTURE`

## 3. Что следует уточнить в STD-008 v0.2

### 3.1. Развести два понятия: «полный прогон» и «автоматическое выполнение»

STD-008 должен явно различать:

1. **FULL SEQUENTIAL TEST** — все входные записи проведены через определённый модуль/последовательность операций;
2. **AUTOMATED RUN** — последовательность выполнена программным агентом по формальному интерфейсу без ручного промежуточного конструирования.

Текущий тест доказал первое, но не второе.

### 3.2. Зафиксировать единый контракт каждого M01–M08

Для каждого модуля необходимы поля:

- `INPUT`
- `OPERATION`
- `OUTPUT`
- `REQUIRED_FIELDS`
- `ID_RULE`
- `TRACE_RULE`
- `STATUS_RULE`
- `COMPLETION_CRITERIA`
- `EXCEPTION_RETURN`
- `PROHIBITIONS`

Это превращает линейную схему в воспроизводимую машину.

### 3.3. Зафиксировать правило кардинальности

Для каждой операции должно быть явно указано отношение:

`1 → 1`, `1 → N`, `N → 1`, `N → N`.

Фактический тест показывает, что разные стадии имеют разные кардинальности:

- Extraction → Distinction: `1 → 1` в текущем полном тесте;
- Distinction → Formulation: `1 → 3`;
- Formulation → Nomenclature: `N → N/1` с возможным сохранением отдельных кандидатов;
- Classification → Passport: `1 → 1`;
- Passport → Relation: `N → M`;
- Passport + Relation → Canonization: `N → M` решений.

Кардинальность должна стать частью контракта, а не оставаться скрытым свойством конкретного запуска.

### 3.4. Развести «кандидата» и «объект» на уровне интерфейса

Нельзя допускать неявного перехода:

`CANDIDATE → OBJECT`

Переход должен проходить через явное производственное решение и статус.

### 3.5. Развести жизненный и эпистемический статус

Жизненный статус:

`ЧЕРНОВИК → ПРОВЕРЕН → КАНОНИЗИРОВАН`

Эпистемический статус:

`UNKNOWN / PROVISIONAL / NEEDS_EVIDENCE / CANONICAL`

Они не должны смешиваться в одном поле.

### 3.6. Сделать отсутствие результата явным результатом

Для каждого входного объекта допустим только один из вариантов:

- создан выходной объект;
- `N/A` с причиной;
- `UNKNOWN`;
- `PROVISIONAL`;
- `NEEDS_EVIDENCE`;
- зарегистрирована производственная причина остановки.

«Не обработан» без статуса — недопустимое состояние.

## 4. Новая формула машины

Предлагается зафиксировать в STD-008 v0.2:

> **MACHINE-SOURCE-001 не обязана производить канон. Она обязана производить прослеживаемый результат с корректно указанной степенью основания.**

И более фундаментально:

> **Машина не должна знать больше, чем позволяют её основания, и не должна терять путь к этим основаниям.**
