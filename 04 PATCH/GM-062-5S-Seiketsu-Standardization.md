## 1. SOURCE

Seiketsu / Standardization — третий из последних шагов 5S после Organization и Neatness.

SOURCE определяет назначение Standardization как установление и поддержание стандарта для предыдущих двух шагов Workplace Organization.

Ключевая SOURCE-логика:

```text
ORGANIZATION + NEATNESS
        ↓
STANDARDIZATION
        ↓
ESTABLISH / MAINTAIN STANDARD
```

SOURCE подчёркивает, что стандарт должен быть понятен и поддерживаем на рабочем месте; визуальные средства и стандартизированные способы поддержания состояния используются для удержания достигнутого уровня. fileciteturn175file0

## 4. DISTINCTIONS — РАЗЛИЧЕНИЯ

### Standardization ≠ Organization

Organization изменяет состав рабочего места; Standardization задаёт способ удержания достигнутого состояния.

### Standardization ≠ Neatness

Neatness определяет размещение required items; Standardization закрепляет способ поддержания результатов предыдущих шагов.

### Establish ≠ Maintain

Установить стандарт и поддерживать стандарт — разные операции.

### Standard ≠ Current State

Стандарт задаёт ожидаемое состояние/способ его поддержания; фактическое состояние может от него отличаться.

### Visual Means ≠ Standard

Визуальные средства могут использоваться для поддержания стандарта, но не являются самим стандартом.

## 11. MACHINE — МАШИНКА

### CANDIDATE MACHINE — Workplace Standardization

```text
INPUT
Achieved Workplace State
(from Seiri + Seiton)
        ↓
[ DEFINE / ESTABLISH STANDARD ]
        ↓
STANDARDIZED EXPECTED STATE
        ↓
[ MAINTAIN STANDARD ]
        ↓
SUSTAINED WORKPLACE CONDITION
```

Инженерный тест:

- **INPUT:** результат предыдущих двух S;
- **OPERATION:** establish + maintain standard;
- **OUTPUT:** стандартизированное ожидаемое состояние;
- **ORGANIZATIONAL EFFECT:** сохранение результатов Organization и Neatness.

**MACHINE = CANDIDATE / SINGLE-SOURCE**

Важно: SOURCE данной вагонетки не раскрывает полный операционный алгоритм стандартизации и не даёт детального цикла проверки. Поэтому их не добавляем.

## 14. CMOC INTERPRETATION

GM-059 и GM-060 изменяли саму рабочую среду:

```text
SEIRI
→ COMPOSITION
```

```text
SEITON
→ LOCATION
```

GM-061 изменяла состояние и одновременно делала возможным его наблюдение:

```text
SEISO
→ CONDITION + CHECKING
```

GM-062 добавляет четвёртую операцию:

```text
SEIKETSU
→ EXPECTED STATE
→ STANDARD
→ MAINTENANCE
```

Отсюда сильная CMOC-гипотеза:

> **После преобразования реальности необходима фиксация ожидаемого состояния, иначе достигнутое изменение не получает механизма устойчивого воспроизведения.**

Это **CMOC INTERPRETATION**, а не SOURCE claim.

Ещё одно различение:

```text
CHANGE STATE
≠
DEFINE EXPECTED STATE
≠
MAINTAIN EXPECTED STATE
```

Именно эта тройка потенциально важна для будущей типологии Машинок.

## 15. СВЯЗЬ С GM-057

GM-057 говорила о systematic approach для **implement and maintain WPO**.

GM-062 показывает один конкретный способ удержания результата: **Standardization**.

Пока не утверждаем, что Standardization исчерпывает Maintenance WPO.
