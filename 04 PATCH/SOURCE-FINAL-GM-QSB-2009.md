# SOURCE-FINAL — GM Quality Systems Basics rev. March 2009

**Source:** GM Quality Systems Basics, rev. March 2009, Global Purchasing and Supply Chain.

## 1. Purpose of this SOURCE-FINAL

This file records the final CMOC-oriented extraction of the source after the page-by-page pass through the QSB strategies. It is an architectural extraction, not a replacement for the source and not a page-by-page transcript.

The source presents eleven QSB strategies as a mutually reinforcing quality-management system:

1. Fast Response
2. Control of Non-Conforming Product
3. Verification Station
4. Standardized Operations
5. Standardized Operator Training
6. Error Proofing Verification
7. Layered Process Audits
8. Risk Reduction / Reverse PFMEA
9. Contamination Control
10. Supply Chain Management
11. Managing Change

The stated strategic result is No Major Disruptions, No PRRs and 0 PPMs / World Class Quality.

## 2. Central architectural finding

Across the source, quality is not presented primarily as a document system. It is produced by interconnected mechanisms that make requirements, process states, deviations, decisions, actions and evidence governable.

The recurring architecture is:

`Requirement → Control → Observable/Measurable State → Detection/Verification → Record → Status/Decision → Action → Evidence → Review/Update`

The source repeatedly converts abstract requirements into operational objects:

- SHALL requirements;
- procedures and work instructions;
- forms and logs;
- named roles;
- approval gates;
- measurements and limits;
- audits;
- action plans;
- verification and trial activities;
- records of actual implementation.

## 3. Contamination Control

Contamination Control is not reduced to cleaning or final inspection. The source manages contamination through source identification, prevention, process monitoring, measurement, records, limits, reaction plans, corrective action and verification of the means of control.

The source distinguishes contamination sources and control areas such as People, Process and Facilities. It also uses specific mechanisms including parts washers, deburring, fluid controls, work-station cleanliness, dunnage/storage controls, process monitoring, SPC/U-Charts, Pareto, reference information, LPA and preventive maintenance.

For retained material in castings, the source distinguishes cleaning from evidence of cleaning: material is collected and weighed, surfaces are visually checked, and results are compared with a standard for the specific part.

Architectural extraction:

`Source → Prevention → Monitoring → Measurement → Record → Limit/Standard → Reaction → Corrective Action`

Strong CMOC principle:

> **Control begins where the system can hold a state that does not have to be directly visible.**

The source also demonstrates a second layer:

`Control measure → verification of control functionality → preventive maintenance → evidence of effectiveness`

## 4. Supply Chain Management

Supply Chain Management extends the control architecture beyond the immediate organization. The source covers multiple tiers of suppliers and expects suppliers to manage their own suppliers systematically.

The recurring structure is:

`Evaluate → Select → Communicate Requirements → Measure Performance → Develop Supplier`

Supplier assessment includes quality-system capability, special processes, labeling, product/process-specific audits and drill-deep/drill-wide problem investigation.

Supplier performance is made observable through metrics, ratings and status indicators. Compliance is distinguished from development/capability: meeting a requirement does not by itself establish a mature or improving capability.

The source also asks why planning, process and controls allowed a defect to occur, moving problem solving from technical cause toward system-level cause.

## 5. Managing Change

Managing Change is treated as controlled transition between accepted process states.

The core PPCR architecture is:

`Change Proposal → Classification/Review → Approval/Rejection → Required Approvals → Written Authorization → Implementation → Implementation Record → Trial/Evaluation where required → Final Approval`

Important distinctions preserved from the source:

- approval ≠ authorization to proceed;
- authorization ≠ implementation;
- implementation ≠ record of implementation;
- implementation ≠ verification/evaluation;
- completion ≠ final approval.

The source explicitly requires planned and emergency changes to be governed. PPCR identifies the change, Change Leader, affected functions, approvals, implementation date and breakpoint.

Rejection is an active control event: the change process stops and concerned parties are notified.

### Production Trial Run

Where required, PTR creates a controlled intermediate verification state:

`Change → Authorization → PTR Readiness → Trial → Evaluation → Acceptance`

Authorization to make a change is therefore not evidence that the changed process has demonstrated acceptable performance.

### Bypass / Backup process

The source treats a bypass as a controlled temporary process, not an informal exception. It has defined entry and exit breakpoints and associated tooling, inspection and audit requirements:

`Normal State → Controlled Bypass State → Verified Return → Normal State`

## 6. Workshop / implementation architecture

The Workshop section provides a mechanism for converting requirements and gaps into organizational action.

The recurring structure is:

`Requirement/SHALL → Current Status → Gap → Proposal → Tracking/Form → Management Review → Action Plan → Implementation`

Teams are cross-functional and aligned with the strategy and competencies required to change the relevant process. Results are presented to Top Management. Unfinished items do not disappear at the closing meeting; they move into the QSB Action Plan.

This supports the CMOC distinction:

> **A diagnosis or review is not complete merely because a gap has been identified; the gap must acquire an action, responsibility and tracking mechanism.**

## 7. Core CMOC distinctions extracted from the source

### D1 — Requirement ≠ Document

A document is a carrier of a requirement/control, not the requirement itself.

### D2 — Compliance ≠ Capability

Current compliance does not by itself prove developed capability.

### D3 — Detection ≠ Control

Detecting a problem does not mean its cause is controlled.

### D4 — Result ≠ Process

Result inspection does not replace process control.

### D5 — Approval ≠ Authorization

Approval and authorization to execute are distinct events.

### D6 — Authorization ≠ Implementation

Permission to execute does not mean execution has occurred.

### D7 — Implementation ≠ Verification

Completion of the action does not prove acceptable performance.

### D8 — Temporary Deviation ≠ Uncontrolled Exception

A temporary deviation can be a defined, bounded and controlled process state.

### D9 — Bypass ≠ Abandonment of Control

When the normal process is bypassed, control must be reconfigured rather than disappear.

### D10 — Workshop ≠ Training

Workshop produces decisions, proposals and action plans, not only knowledge.

### D11 — Problem ≠ Corrective Action

An action is not proof that the systemic cause has been removed.

### D12 — Supplier ≠ Purchase Source

A supplier is treated as a managed capability within an extended system.

### D13 — Change ≠ New State

The act of deciding to change is not the same as establishing and accepting the new controlled state.

The source provides evidence for the following CMOC mechanism families:

- Problem Resolution Tracking;
- PPCR / Change Control;
- Decision Gates;
- Production Trial Run;
- Bypass / Backup Process Control;

These are mechanism candidates, not all canonical CMOC Machines. A mechanism becomes a Machine candidate only after its purpose, input/output, state transition, trigger, responsibility and evidence are sufficiently defined.

## 9. Machine extraction rule confirmed by the source

The source supports a bottom-up rule:

`Problem → Source/Risk → Control Method → Mechanism → Machine (if independently realizable)`

Therefore not every QSB practice should be canonized as a Machine. Some are:

- mechanisms;
- control patterns;
- decision gates;
- states;
- records;
- roles;
- evidence structures;
- integrated control loops.

## 10. Final CMOC interpretation

The deepest contribution of the source is not the individual QSB tools. It is the repeated demonstration that organizational control is achieved by governing transitions and states with explicit requirements, evidence, decisions, responsibilities and actions.

A compact CMOC representation of the source is:

`Requirement → State Definition → Control Mechanism → Observation/Measurement → Record → Status → Decision → Action → Verification → Accepted State`

For changes:

`Current Accepted State → Change Object → Review → Authorization → Implementation → Evidence → Verification → New Accepted State`

For risk/problem control:

`Risk/Problem → Source/Cause → Preventive/Detective Control → Evidence → Response → System Update`
