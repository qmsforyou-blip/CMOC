# M08 — Критерии необходимости третьего контрольного прогона

Дата: 18-09-2026

## 1. Назначение

Определить, нужен ли третий прогон M08 после выявления вариантов Run A/B и формализации DECISION RULE v0.1.

Третий прогон не выполняется автоматически. Он оправдан только если должен проверить конкретную гипотезу о технологии.

## 2. Что уже проверено

- Run A и Run B выполнены без передачи результатов одного прогона в другой.
- M01–M06 показали воспроизводимость структуры и семантики на 40 объектах.
- M07 после нормализации идентичности конечных точек: 25/25 MATCH.
- M08 выявил расхождения, связанные с границей доказательности.
- DECISION RULE v0.1 формализовала последовательность:
  Evidence → Object Boundary → Type Assignment → Decision.
- QC-001 применил правило ко всем 40 объектам:
  40/40 решений; 38 PROVISIONAL; 2 NEEDS_EVIDENCE; 0 решений без EVIDENCE_GAP.

## 3. Когда третий прогон НУЖЕН

Третий прогон нужен, если существует хотя бы одна из следующих проверяемых гипотез:

1. **Правило может давать разные решения при повторном применении к тем же входам.**
2. **Формулировка правила допускает несколько трактовок одного и того же критерия.**
3. **Есть классы объектов, для которых порядок Evidence → Boundary → Type работает иначе, чем для остальных.**
4. **После QC-001 остаются NEEDS_EVIDENCE, границы которых неоперационализированы и могут быть оценены по-разному.**

В этом случае третий прогон должен проверять именно правило, а не заново добывать содержание источника.

## 4. Когда третий прогон НЕ НУЖЕН

Он не нужен, если QC-001 одновременно подтверждает:

- полноту 40/40;
- обязательность конкретного EVIDENCE_GAP;
- однозначность последовательности критериев;
- отсутствие зависимости от порядка и имени объекта;
- отсутствие скрытого unresolved gap под PROVISIONAL;
- возможность воспроизвести решение по фиксированной процедуре;
- отсутствие неразрешённой альтернативной трактовки самого правила.

В таком случае третий прогон будет повторением уже проведённого контроля, а не новым тестом.

## 5. Особенность текущего результата

Два оставшихся NEEDS_EVIDENCE — 009 и 012 — сами по себе не доказывают дефект правила.

Они показывают наличие **содержательно неразрешённых границ объектов**. Это нормальный результат source-bound канонизации и не является основанием для дополнительного прогона, если правило одинаково обрабатывает такие границы.

Следовательно, проверять необходимо не «исчезнут ли 009 и 012», а **одинаково ли правило классифицирует аналогичные boundary gaps**.

## 6. Архитектурное решение

Если отдельный анализ не обнаружит неоднозначности самого DECISION RULE v0.1, третий M08 не запускать.

Следующая операция:

**QC-001 → решение о достаточности → STD-008 v0.3**

Если будет обнаружена неоднозначность правила, сначала создать PATCH на правило и только затем определить дизайн третьего контрольного прогона.

## 7. Принцип

> Третий прогон нужен не для увеличения количества прогонов, а для проверки конкретной гипотезы, которую нельзя проверить уже выполненным контролем.
