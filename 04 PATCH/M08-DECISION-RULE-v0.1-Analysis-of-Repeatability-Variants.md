# M08 DECISION RULE — ANALYSIS OF REPEATABILITY VARIANTS

Дата: 18-09-2026

## Назначение

Определить воспроизводимый критерий M08 для различения:

`PROVISIONAL` ↔ `NEEDS_EVIDENCE`

без изменения результатов исторических Run A и Run B.

## Исходное наблюдение

После исправления сверки Run A и Run B имеют одинаковые 40 паспортных объектов.

Нестабильны 8 решений:

- Run A → NEEDS_EVIDENCE: 001, 003, 005, 006, 007, 008;
- Run B → NEEDS_EVIDENCE: 012, 019;
- общий NEEDS_EVIDENCE: 002, 009.

Итого: **32 MATCH / 8 VARIANT / 0 DIVERGENCE**.

Следовательно, исходный M08 использовал недостаточно формализованный критерий.

## Разбор восьми вариантов

### 001 — Руководство по управлению претензиями

Источник прямо представляет себя как руководство по управлению претензиями. Основание для существования source-bound объекта есть. Однако `GUIDANCE` — классификационная категория, а не автоматически CMOC-тип.

**Вывод:** `PROVISIONAL` обоснован. `NEEDS_EVIDENCE` только из-за типа `GUIDANCE` не должен назначаться.

### 003 — Область применимости процесса жалоб

Источник имеет явный раздел «1 Область применения» и прямо задаёт границы применения процесса управления претензиями: связанные с продукцией планирование, разработка, производство, обслуживание и улучшение; отдельно указаны исключения. fileciteturn118file0

**Вывод:** для source-bound паспорта основание достаточно. Тип `SCOPE` сам по себе не является дефицитом доказательств. `PROVISIONAL`.

### 005 — Функции процесса работы с жалобами

Источник явно перечисляет аспекты работы с претензиями, включая создание процесса, анализ и оценку претензий, аудит и анализ результативности/эффективности процесса. fileciteturn118file0

**Вывод:** функции непосредственно поддержаны источником. `PROVISIONAL`.

### 006 — Интеграция процесса в СМК

Источник прямо указывает, что процесс управления претензиями может использоваться как один из процессов системы менеджмента качества. fileciteturn118file0

**Вывод:** основание для source-bound объекта есть. `PROVISIONAL`.

### 007 — Жизненный цикл процесса жалоб

Источник связывает руководство с планированием, разработкой, производством, обслуживанием и улучшением и далее описывает последовательность обработки претензии: регистрация, первоначальная оценка, расследование, ответ/решение и закрытие.

**Вывод:** `PROVISIONAL`; само наличие составного жизненного цикла не является автоматически `NEEDS_EVIDENCE`.

### 008 — Условия эффективности процесса

Источник прямо требует условий для результативного и эффективного процесса: политика, процедуры и цели, ресурсы, обучение, доступность, мониторинг и анализ. В частности, раздел 5.2 задаёт связь политики с процедурами и целями, а 5.3 — ресурсы и ответственность. fileciteturn118file0

**Вывод:** основание достаточно для source-bound объекта. `PROVISIONAL`.

### 012 — Цель, политика и процесс

Источник прямо связывает политику с процедурами и целями процесса: на основе политики должны быть установлены процедуры и цели процесса управления претензиями. fileciteturn118file0

Но кандидат объединяет три разных понятийных уровня в один объект: `цель + политика + процесс`.

**Вывод:** здесь есть реальный риск границы объекта. `NEEDS_EVIDENCE` может быть обоснован не отсутствием источника, а необходимостью подтвердить, что это один объект, а не три связанных объекта.

### 019 — Представитель руководства

Источник имеет отдельный подраздел 5.3.2 и прямо задаёт роль представителя руководства, его ответственность и действия. fileciteturn118file0

Основание существования роли как source-bound объекта сильное. Но для CMOC требуется проверить, является ли это самостоятельным универсальным `ROLE`, либо ролью, специфичной для данного процесса.

**Вывод:** `NEEDS_EVIDENCE` может быть обоснован именно вопросом границы/универсальности типизации, а не отсутствием фактического основания.

## Ключевое различение

`NEEDS_EVIDENCE` нельзя использовать как синоним:

- «тип мне не нравится»;
- «объект сложный»;
- «объект ещё не канонизирован»;
- «объект может оказаться составным» без указания конкретного доказательного дефицита.

Он должен означать:

> **существует конкретный незакрытый вопрос, ответ на который требует дополнительного доказательства, необходимого для принятия решения о границе, типе или идентичности объекта.**

## Предлагаемый M08 DECISION RULE v0.1

### Шаг 1 — Source Evidence

Есть ли в текущем SOURCE прямое основание существования кандидата?

- НЕТ → `NEEDS_EVIDENCE`
- ДА → Шаг 2

### Шаг 2 — Object Boundary

Можно ли однозначно установить границу кандидата как одного объекта на основании текущего SOURCE + PAS?

- НЕТ → `NEEDS_EVIDENCE`
- ДА → Шаг 3

### Шаг 3 — Type Assignment

Можно ли установить назначенный CLASS без дополнительного внешнего основания?

- НЕТ → `NEEDS_EVIDENCE`
- ДА → Шаг 4

### Шаг 4 — Source-Bound Decision

Объект имеет достаточное основание для фиксации, но ещё не прошёл межисточниковую CMOC-канонизацию:

→ `PROVISIONAL`

### Шаг 5 — Canonical Decision

`CANONICAL` разрешается только при выполнении отдельного критерия CMOC-канонизации; один источник сам по себе его не создаёт.

## Важное следствие

`NEEDS_EVIDENCE` — это не уровень «слабого кандидата».

Это **exception state**, который обязан содержать конкретный `EVIDENCE_GAP`.

Минимальное поле:

`EVIDENCE_GAP: <что именно не доказано и какое доказательство требуется>`

Без `EVIDENCE_GAP` решение `NEEDS_EVIDENCE` считается неполным.

## Предварительная проверка

По этому правилу:

- 003, 005, 006, 007, 008 имеют достаточное source evidence и должны оставаться `PROVISIONAL`, если не указан конкретный boundary/type gap.
- 001 — `PROVISIONAL`, если не выявлен конкретный gap по boundary/type.
- 012 — `NEEDS_EVIDENCE` может быть сохранён из-за composite boundary: `цель / политика / процесс`.
- 019 — `NEEDS_EVIDENCE` может быть сохранён при явно сформулированном вопросе универсальности `ROLE` за пределами данного процесса.
- 002 и 009 требуют отдельного подтверждения, поскольку оба прохода независимо сохранили `NEEDS_EVIDENCE`.

## Что НЕ делаем

- не изменяем Run A;
- не изменяем Run B;
- не объявляем Run B автоматически правильным;
- не делаем третий прогон до формализации правила;
- не повышаем `NEEDS_EVIDENCE` до `PROVISIONAL` только ради статистической повторяемости.

## Следующий контроль

Применить M08 DECISION RULE v0.1 ко всем 40 объектам.

Цель контроля:

1. каждый `NEEDS_EVIDENCE` имеет конкретный `EVIDENCE_GAP`;
2. ни один `PROVISIONAL` не скрывает известный unresolved gap;
3. правило одинаково применяется к объектам разных CLASS;
4. решение не зависит от порядка объекта или формулировки имени;
5. результаты исторических Run A/B остаются неизменными.

После этого принять решение о `STD-008 v0.3` или отдельном нормативном PATCH.
