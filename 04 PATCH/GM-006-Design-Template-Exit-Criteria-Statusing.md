## 1. LOCATION

Ключевой фрагмент — **1.2 Fast Response**, pp. 14–18.

GM показывает физическую конструкцию Fast Response Tracking Board и её пример. Board строится как 2-sided construction с plywood, plotter matrix и plexiglas; предусматриваются Open PRR List и Fast Response Sign-in. Board размещается в зоне meeting для оптимизации visual management. fileciteturn74file6

На Board GM предлагает проверять как минимум:

- Ownership;
- Exit Criteria;
- Overall Status;
- Next Report Out Date.

Для Red или Yellow указывается Target Date, когда ожидается переход в Green. fileciteturn74file6

Далее GM задаёт конструкцию Exit Criteria и правила статусирования: exit criteria устанавливаются для каждого ключевого шага problem solving; документируются также возможности validation corrective action через LPA и prevention of recurrence через error proofing и institutionalized Lessons Learned. Evidence каждого criterion рассматривается Owner на Fast Response Meeting; leadership approval позволяет закрыть issue / перевести его в Green. fileciteturn73file1

## 3. DISTINCTIONS

### DIS-GM-006-01

**Issue ≠ Exit Criterion.**

Issue является объектом управления; Exit Criteria задают условия, при которых соответствующий шаг может считаться завершённым.

### DIS-GM-006-02

**Exit Criterion ≠ Status.**

Criterion задаёт условие завершения; Status показывает текущее состояние относительно заданного timing / completion.

### DIS-GM-006-03

**Status ≠ Evidence.**

GM требует review evidence каждого criterion. Следовательно, Green не является просто визуальным состоянием: за ним должно стоять рассмотренное evidence. fileciteturn73file1

### DIS-GM-006-04

**Item Status ≠ Overall Status.**

Overall Status определяется как R, Y или G и берётся по худшему состоянию любого отдельного item слева. fileciteturn75file0

### DIS-GM-006-05

**Timing ≠ Status.**

Timing каждого Exit Criterion устанавливается отдельно. Default при открытии проблемы — Yellow; при превышении timing — Red; при completion — Green. fileciteturn73file5

### DIS-GM-006-06

**Green ≠ просто “проблема закрыта”.**

GM связывает переход в Green с выполнением criterion и review evidence, а окончательное закрытие требует leadership approval. fileciteturn73file1

### DIS-GM-006-07

**Red ≠ только плохой цвет.**

Для Red GM требует показывать expected date to be Green и details следующего шага в action/status comment column. fileciteturn73file5

### DIS-GM-006-08

**Local item status ≠ overall system signal.**

Overall Status агрегирует worst condition отдельного item; таким образом локальные состояния превращаются в один управленческий сигнал.

## 5. EXTRACTION — КОНСТРУКЦИЯ

GM даёт Board как материальный и визуальный носитель нескольких управленческих состояний одновременно:

```text
ISSUE
 │
 ├── Ownership
 ├── Exit Criteria
 ├── Timing
 ├── Next Report Out Date
 ├── Target Date
 ├── Action / Status Comment
 └── Overall Status (R/Y/G)
```

При этом Exit Criteria привязаны к шагам problem solving:

```text
Problem Solving Step
        ↓
Exit Criterion
        ↓
Timing
        ↓
Evidence
        ↓
Review
        ↓
Status R / Y / G
        ↓
Green + Leadership Approval
```

В качестве примера GM показывает:

```text
Problem opened: 1/21
        ↓
Containment ≤ 24 h
        ↓
Root Cause ≤ 7 days
        ↓
Corrective Action ≤ 14 days
        ↓
если срок превышен → RED
        ↓
expected date to Green
```

## 10. MECHANISM

### CANDIDATE — Statusing / Closure Control Mechanism

Здесь SOURCE уже даёт достаточно плотную последовательность:

1. для каждого key step устанавливается Exit Criterion;
2. устанавливается timing;
3. текущее состояние получает R/Y/G;
4. evidence рассматривается Owner;
5. Leadership принимает решение о закрытии / Green;
6. Overall Status определяется худшим item.

Таким образом status не является свободной оценкой участника. Он связан с **criterion + timing + evidence + review**.

## 17. CMOC INTERPRETATION

Главная добыча GM-006:

> **Статус становится управленческим объектом только тогда, когда он привязан к критерию, времени и основанию для его определения.**

И ещё сильнее:

> **Overall Status — это не мнение о состоянии системы, а результат правила агрегации локальных состояний по худшему условию.**

Это уже очень близко к инженерной конструкции машинки:

```text
FACT / CONDITION
      ↓
CRITERION + TIMING
      ↓
STATUS
      ↓
AGGREGATION
      ↓
MANAGEMENT SIGNAL
```

При этом **Evidence** вводит ещё один слой:

```text
Claim of completion
      ↓
Evidence
      ↓
Review
      ↓
Approval
      ↓
Green / Closure
```

Это важное различение для последующего сопоставления с ISO, но здесь мы фиксируем его пока исключительно как **GM SOURCE CLAIM**.
