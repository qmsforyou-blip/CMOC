## 3. DISTINCTIONS

### DIS-GM-002-01

Следует различать **Fast Response meeting** и **Problem Solving**. GM прямо определяет meeting как communications meeting, not a problem solving meeting. Problem Solving выполняется владельцем вне meeting.

### DIS-GM-002-02

Следует различать **Issue** и **Owner**. Issue должен иметь назначенного владельца; site leadership назначает natural owner, если он не был назначен ранее.

### DIS-GM-002-03

Следует различать **Overall Status** и состояние отдельных критериев. Overall Status определяется худшим состоянием отдельного item.

### DIS-GM-002-04

Следует различать **Status** и **Exit Criteria**. Status определяется относительно установленных критериев выхода и их timing; критерии выхода должны быть определены для ключевых шагов.

### DIS-GM-002-05

Следует различать **текущее состояние** и **ожидаемую дату изменения состояния**. Для Red/Yellow GM требует Target Date expected to go Green; красный статус сопровождается action/status comment с объяснением следующего шага.

### DIS-GM-002-06

Следует различать **Board как физическую/визуальную форму** и **процесс Fast Response**, в который Board встроена. Источник требует не просто наличия формы, а её обновления владельцем, использования на meeting и периодического report out.

### DIS-GM-002-07

Следует различать **документирование issue** и **управление его статусом**. PPSR или equivalent обеспечивает структуру report out; Tracking Board обеспечивает визуальное отслеживание issue, ownership, exit criteria и status.

### DIS-GM-002-08

Board содержит не только описание проблемы. В показанном GM примере в ней представлены последовательные элементы прохождения проблемы: Containment, Root Cause Identified, Corrective Action Implemented, Error Proof/Detection, LPA, Corrective Action Validated, PFMEA/CP Updated, Standard Work/Operator Instructions, Lessons Learned, а также Action Plan/Countermeasure и даты закрытия.

## 5. EXTRACTION — КОНСТРУКЦИЯ BOARD

Показанный GM пример является не пустой таблицей, а заполненной рабочей формой. В ней присутствуют, в частности:

```text
ITEM #
Date Opened
Who Called
Who Answered
Customer
Concern # / Field Rep Ranking
Program / Product Name
Issue Description
Owner
Next Report Date By Owner

Containment - Breakpoint
Root Cause Identified
Corrective Action Implemented
Error Proof / Detection
Layered Process Audits
Corrective Action Validated
PFMEA / CP Updated
Standard Work / Operator Instructions
Lessons Learned (Institutionalized)

Action Plan / Countermeasure
Forecasted Closed Date
Actual Closed Date
Customer Closed Date

OVERALL STATUS (R/Y/G)
```

Источник также задаёт status key:

```text
Y = initial / within timing
R = timing exceeded / not complete
G = completed
```

И отдельно показывает пример, где проблема открыта 1/21, containment выполнен за 24 часа, root cause определён за 7 дней, corrective action не выполнен за 14 дней → Red, с ожидаемой датой перехода в Green.

## 10. MECHANISM

### CANDIDATE

**Fast Response Tracking Board** обладает признаками организационного механизма, поскольку GM связывает её с обязательными действиями:

1. issue должен быть внесён;
2. должен быть назначен owner;
3. должны быть определены exit criteria;
4. для критериев задаётся timing;
5. состояние визуально кодируется R/Y/G;
6. owner обязан обновлять Board;
7. status используется в meeting;
8. завершение определяется через exit criteria и evidence.

Однако **механизм ещё не канонизируется**.

## 13. MACHINE

### **CANDIDATE MACHINE**

**Fast Response Tracking Board**

Предварительная функциональная модель:

```text
INPUT
Significant Quality Concern / Issue
        ↓
TRANSFORMATION
Identification
+ Ownership
+ Exit Criteria
+ Timing
+ Statusing
+ Action / Progress Tracking
        ↓
OUTPUT
Visible, owned, statused and trackable issue
        ↓
RESULT
Организация может видеть состояние проблемы,
назначенного владельца, ожидаемый переход,
критерии закрытия и отклонение по срокам.
```

### Почему это кандидат именно на Machine

Не потому, что это «таблица».

А потому, что GM задаёт воспроизводимое преобразование организационного состояния:

```text
неструктурированная / возникшая проблема
              ↓
        Tracking Board
              ↓
структурированный управляемый issue
```

Важное ограничение: **Board не решает корневую причину сама**. Problem Solving остаётся отдельным элементом Fast Response. Поэтому Board не следует отождествлять с машиной Problem Solving.
