## 1. LOCATION

Фрагмент вводит Problem Solving после Fast Response и задаёт его исходную оптику: что считать проблемой и какие принципы должны предшествовать причинному анализу.

GM определяет problem как GAP между текущей ситуацией и удовлетворённостью customer, а также как discrepancy между существующим Standard или Expectation и Actual Situation. Для Problem Solving организация должна иметь определённый процесс и стандарт документирования используемых инструментов для идентификации и устранения root cause.

## 3. DISTINCTIONS

### DIS-GM-008-01

**Problem ≠ просто нежелательный результат.**

GM определяет Problem через discrepancy между Standard / Expectation и Actual Situation.

### DIS-GM-008-02

**Standard / Expectation ≠ Actual Situation.**

Проблема возникает в различии между тем, что должно происходить, и тем, что фактически происходит.

```text
STANDARD / EXPECTATION
          ↓
       GAP / DISCREPANCY
          ↑
   ACTUAL SITUATION
```

fileciteturn82file0

### DIS-GM-008-03

**Problem identification ≠ cause analysis.**

GM требует сначала получить thorough grasp of what is actually happening и только после этого переходить к cause analysis.

### DIS-GM-008-04

**Opinion ≠ data.**

GM прямо требует не реагировать на problems без data и принимать решения на основании фактов, а не мнений.

### DIS-GM-008-05

**Observed abnormality ≠ assumed cause.**

Сначала следует увидеть abnormal occurrence и Point of Cause first hand; причинный анализ откладывается до достаточного понимания ситуации.

### DIS-GM-008-06

**Root cause ≠ первая найденная причина.**

GM связывает продолжение вопроса “Why?” с достижением возможности prevent reoccurrence by addressing the root cause.

### DIS-GM-008-07

**Problem Solving ≠ индивидуальная импровизация.**

Организация должна иметь defined process for Problem Solving и standard for documenting tools used for root cause identification and elimination.

## 5. EXTRACTION

GM задаёт предварительный преобразователь до собственно поиска root cause:

```text
ACTUAL SITUATION
      +
STANDARD / EXPECTATION
      ↓
DISCREPANCY / GAP
      ↓
PROBLEM DEFINITION
      ↓
DATA + FIRST-HAND OBSERVATION
      ↓
THOROUGH GRASP OF SITUATION
      ↓
CAUSE / EFFECT
      ↓
ROOT CAUSE
```

При этом порядок принципиален: cause analysis не должен начинаться до grasp of the situation.

## 10. MECHANISM

### CANDIDATE — Problem Framing / Cause Analysis Discipline

Источник даёт достаточно материала для кандидатного механизма дисциплинирования problem solving:

1. установить Standard / Expectation;
2. установить Actual Situation;
3. определить Gap / Discrepancy;
4. собрать data;
5. увидеть abnormal occurrence / Point of Cause first hand;
6. получить thorough grasp of situation;
7. только затем анализировать cause / effect;
8. продолжать “Why?” до root cause, позволяющей prevent reoccurrence.

Механизм здесь пока не равен полному GM Problem Solving Process: дальнейшие конкретные шесть шагов будут добыты отдельными вагонетками.

## 17. CMOC INTERPRETATION

Главная добыча GM-008:

> **Проблема существует не как “плохой результат”, а как фиксируемое различие между тем, что должно быть, и тем, что фактически есть.**

И второй, ещё более сильный вывод:

> **Причинный анализ должен быть отложен до тех пор, пока система не получила достаточное фактическое представление о ситуации.**

В инженерной форме:

```text
EXPECTATION
      ↓
ACTUAL
      ↓
GAP
      ↓
PROBLEM
      ↓
FACTS
      ↓
UNDERSTANDING
      ↓
CAUSE
      ↓
ROOT CAUSE
```

Это создаёт важный барьер против преждевременного объяснения проблемы.

И именно поэтому **“не реагировать без данных”** и **“увидеть Point of Cause first hand”** являются не просто советами GM, а кандидатами на устойчивые правила организационной работы. fileciteturn85file11
