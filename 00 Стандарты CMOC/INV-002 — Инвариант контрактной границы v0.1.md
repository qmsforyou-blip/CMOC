# INV-002 — Инвариант контрактной границы v0.1

**Дата:** 18-09-2026  
**Статус:** SUPPORTED BY CONTROL TEST  
**Основание:** INV-001 + ARCH-002 + CONTROL-RUN-012

---

## 1. Инвариант

> **HANDOFF не означает автоматическую приемку результата следующей машиной.**

Каждый переход:

`OUTPUT₁ + HANDOFF → INPUT₂`

обязан пройти проверку совместимости с контрактом следующей MACHINE.

Минимальная форма:

`OUTPUT₁ + HANDOFF → CONTRACT CHECK → ACCEPT / REJECT`

---

## 2. ACCEPT

Переход разрешён только если:

- INPUT соответствует REQUIRED_INPUT;
- обязательные поля присутствуют;
- статус входа допустим;
- traceability сохранена;
- другие условия TASK CONTRACT выполнены.

После ACCEPT:

`INPUT₂ → MACHINE₂ → OUTPUT₂`

---

## 3. REJECT

Если хотя бы одно обязательное условие контракта не выполнено:

`CONTRACT CHECK → REJECT`

Цепочка не должна продолжаться молча.

Минимальный результат:

`REJECT + REASON`

Примеры причин:

- CONTRACT_MISMATCH;
- MISSING_INPUT;
- MISSING_TRACE;
- INVALID_STATUS;
- QC_FAIL;
- UNKNOWN.

---

## 4. Запрещённое поведение

При REJECT оркестратор не должен:

- самостоятельно выполнять пропущенный TASK;
- преобразовывать несовместимый OUTPUT в требуемый INPUT без отдельного контракта;
- обращаться к SOURCE для молчаливого восстановления отсутствующего промежуточного результата;
- использовать скрытую память предыдущего прохода;
- передавать несовместимый INPUT следующей MACHINE;
- создавать downstream OUTPUT до устранения причины отказа.

---

## 5. Разделение ответственности

`MACHINE` отвечает за производство.

`CONTRACT` отвечает за допустимость входа/выхода.

`ORCHESTRATOR` отвечает за проверку границы и маршрутизацию.

Поэтому оркестратор не должен исправлять производственный результат «по смыслу» вместо машины.

---

## 6. Доказательная база

CONTROL-RUN-012 построен как отрицательный тест:

`M02 OUTPUT = Distinction Records`

при этом:

`M04 REQUIRED INPUT = Formulation Records`

Проверяемое различие:

`Distinction Record ≠ Formulation Record`

Ожидаемый результат:

`CONTRACT_MISMATCH → STOP`

Тест предназначен для проверки архитектурного правила отрицательного перехода.

---

## 7. Граница доказательства

Зафиксированный тест поддерживает сам принцип контрактной границы.

Он не доказывает:

- автоматическую проверку всех возможных контрактов;
- корректность всех существующих TASK CONTRACT;
- автоматический выбор альтернативного маршрута;
- автоматическое исправление несовместимого INPUT;
- универсальность механизма для любой реализации суперагента.

---

## 8. Архитектурная формула

`HANDOFF = TRANSFER`

`CONTRACT CHECK = GATE`

`ACCEPT = CONTINUE`

`REJECT = STOP + REASON`

Следовательно:

`OUTPUT → HANDOFF → CONTRACT CHECK → {ACCEPT | REJECT}`

---

## 9. Следствие для суперагента

Суперагент должен рассматривать каждую границу между MACHINE как **контрактный gate**.

Его задача не «догадаться, что имелось в виду», а:

1. проверить контракт;
2. разрешить переход;
3. либо остановить цепочку с явной причиной.

Это делает отказ нормальным производственным результатом, а не исключением из архитектуры.

---

## 10. Следующий проверяемый вопрос

Проверить второй тип отрицательного перехода:

`OUTPUT соответствует типу INPUT,`

но отсутствует обязательное поле/трассировка.

Цель — отличить:

`TYPE MATCH`

от

`CONTRACT MATCH`.

То есть проверить, что одного совпадения типа недостаточно для ACCEPT.
