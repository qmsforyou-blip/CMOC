# ARCH-002 — Архитектура оркестрации производственных машин v0.1

**Версия:** v0.1  
**Дата:** 18-09-2026  
**Статус:** Working Architectural Record  
**Основание:** ARCH-001 + INV-001 + CONTROL-RUN-011

---

## 1. Назначение

Зафиксировать архитектурную роль суперагента как оркестратора независимых производственных машин.

Документ не определяет новую семантику TASK и не расширяет доказательную область CONTROL-RUN-011. Он формализует уже установленное различение между MACHINE и оркестрацией.

---

## 2. Базовый принцип

**Суперагент не является носителем производственного знания конкретной цепочки.**

Его функция:

PLAN → SELECT MACHINE → BIND INPUT → EXECUTE TASK → VALIDATE OUTPUT → HANDOFF → NEXT

Производственное знание находится в машинах, контрактах и явных результатах, а не в скрытом состоянии оркестратора.

---

## 3. Разделение ответственности

| Компонент | Ответственность |
|---|---|
| INVARIANT | задаёт архитектурные ограничения |
| MACHINE | выполняет стандартизированную операцию |
| TASK CONTRACT | определяет допустимые входы и выход операции |
| SOURCE PACKAGE | предоставляет материал |
| BATCH | идентифицирует конкретное выполнение |
| OUTPUT | фиксирует результат операции |
| HANDOFF | явно передаёт результат |
| SUPERVISOR / SUPERAGENT | организует последовательность и проверяет контракты |

Суперагент **не должен** подменять MACHINE содержанием собственного скрытого рассуждения.

---

## 4. Минимальный orchestration contract

INPUT + TASK + MACHINE + CONTRACT → BATCH → OUTPUT

После завершения:

OUTPUT + HANDOFF → следующая операция

Если контракт следующей операции не принимает данный OUTPUT, цепочка не продолжается молча. Возвращается явная причина:

- CONTRACT_MISMATCH;
- MISSING_INPUT;
- MISSING_TRACE;
- INVALID_STATUS;
- QC_FAIL;
- UNKNOWN.

---

## 5. Машина не хранит состояние цепочки

Состояние перехода должно находиться в явных артефактах:

BATCH + OUTPUT + TRACEABILITY + HANDOFF

а не в:

- истории чата;
- неявной памяти агента;
- незаписанном промежуточном решении;
- предположении, что предыдущий TASK уже выполнялся.

---

## 6. Минимальная цепочка

Пример проверенной архитектурной формы:

SOURCE_PACKAGE

→ TASK=M01

→ BATCH₁

→ OUTPUT₁

→ explicit HANDOFF

→ TASK=M02

→ BATCH₂

→ OUTPUT₂

→ explicit HANDOFF

→ TASK=M03

→ BATCH₃

→ OUTPUT₃

CONTROL-RUN-011 подтвердил такую форму для цепочки M01→M02→M03 на SRC-002 в пределах указанного теста.

---

## 7. Проверки оркестратора

Перед запуском TASK:

1. SOURCE/TASK идентифицированы;
2. MACHINE определена;
3. контракт TASK известен;
4. вход соответствует контракту;
5. BATCH_ID создан;
6. traceability задана.

После TASK:

1. OUTPUT создан либо явно возвращён результат отсутствия;
2. статус зафиксирован;
3. traceability сохранена;
4. QC выполнен;
5. HANDOFF объявлен либо цепочка остановлена.

---

## 8. Отсутствие скрытого перехода

Запрещён переход вида:

OUTPUT₁ → ??? → INPUT₂

где промежуточный механизм существует только в контексте агента.

Допустимый переход:

OUTPUT₁ + HANDOFF_CONTRACT → INPUT₂

Следовательно, цепочка должна быть восстанавливаема по артефактам без знания внутреннего контекста оркестратора.

---

## 9. Что доказано

На основании имеющихся контрольных прогонов установлено:

- MACHINE может работать с разными SOURCE;
- проверено изменение TASK при сохранении MACHINE и SOURCE;
- OUTPUT одного TASK может быть явным INPUT следующего;
- BATCH различает отдельные выполнения;
- в проверенной цепочке M01→M02→M03 скрытая зависимость от предыдущего результата не использовалась;
- traceability сохраняется через переходы.

---

## 10. Что не доказано

Пока не следует считать доказанными:

- универсальный оркестратор для любых MACHINE;
- автоматическую проверку любого TASK CONTRACT;
- автоматический выбор оптимальной цепочки;
- автоматическую коррекцию ошибочных OUTPUT;
- полную автоматизацию M01–M08 без дополнительных контрольных условий;
- отсутствие скрытого состояния во всех возможных реализациях суперагента.

---

## 11. Архитектурная формула

SUPERAGENT = ORCHESTRATION

MACHINE = PRODUCTION

CONTRACT = INTERFACE

BATCH = EXECUTION

OUTPUT = ARTIFACT

HANDOFF = TRANSFER

Поэтому:

> Суперагент должен соединять машины контрактами, а не заменять машины своим контекстом.

---

## 12. Следующий проверяемый вопрос

Следующий эксперимент должен проверить не новую семантику, а **контрактную сборку цепочки**:

MACHINE₁ → CONTRACT → MACHINE₂

с намеренным изменением одного из условий входа и обязательной фиксацией отказа.

Цель — проверить, что оркестратор умеет не только продолжать корректную цепочку, но и **останавливать некорректную цепочку по контракту**.
