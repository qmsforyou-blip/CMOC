# STD-008 — MACHINE-SOURCE-001
## Машина добычи инженерного знания

**Версия:** v0.8  
**Дата:** 20-09-2026  
**Статус:** Standard  
**Основание редакции:** v0.7 + production automated M01–M08 run on SRC-002 + controlled M07/M08 NO_RELATION branch.

---

## 1. Назначение

MACHINE-SOURCE-001 реализует последовательность:

`SOURCE → EXTRACTION → DISTINCTIONS → FORMULATIONS → NOMENCLATURE → CLASSIFICATION → PASSPORT → RELATIONS → CANONIZATION`

Машина должна обеспечивать:

- сохранение происхождения результата;
- передачу результата следующему модулю без обязательного повторного чтения SOURCE;
- обратную трассировку результата к основанию;
- явную фиксацию неопределённости;
- невозможность незаметно подменить источник интерпретацией;
- воспроизводимость производственного прохода.

**Главное правило:**

> Машина не должна знать больше, чем позволяют её основания, и не должна терять путь к этим основаниям.

---

## 2. Граница машины

Один логический `SOURCE` + один определённый производственный проход = один `BATCH`.

`SOURCE_PACKAGE` может содержать несколько файлов одного логического Источника.

История производственных результатов append-only. Старый Batch не изменяется скрытым образом. Ошибка, уточнение, спор, аудит или новый материал основания создают новый проход/ревизию.

---

## 3. Модули и контракты

Каждый модуль обязан иметь:

`INPUT / OPERATION / OUTPUT / REQUIRED_FIELDS / ID_RULE / TRACE_RULE / STATUS_RULE / COMPLETION_CRITERIA / EXCEPTION_RETURN / PROHIBITIONS`

| Модуль | Вход | Операция | Выход | Кардинальность |
|---|---|---|---|---|
| M01 | SOURCE_PACKAGE | проверка и фиксация Источника | Extraction Batch | 1→1 |
| M02 | Extraction Record OR SOURCE_PACKAGE when explicitly contracted | извлечение различения | Distinction Record | 1→1* |
| M03 | Distinction OR SOURCE_PACKAGE when explicitly contracted | три уровня формулировки | Formulation Records | 1→3 |
| M04 | Formulation Records | выделение кандидатов номенклатуры | Nomenclature Candidates | N→N/1 |
| M05 | Nomenclature Candidate | рабочая типизация | Classification Record | 1→1 |
| M06 | Classification Record | сборка паспорта | Passport Record | 1→1 |
| M07 | Passport Records | выделение отношений | Relation Candidate | N→M |
| M08 | Passport + Relation Candidate where applicable | решение о канонизации | Canonization Decision | N→M |

`*` 1→1 является проверенной схемой полного теста; другие кардинальности M02 требуют отдельной фиксации в конкретном контракте.

Кардинальность является свойством операции и не должна подразумеваться только по факту конкретного запуска.

---

## 4. Минимальная трассировка

Базовая цепочка:

`SOURCE_ID → BATCH_ID → EXTRACTION_RECORD_ID → DISTINCTION_ID → FORMULATION_ID → NOMENCLATURE_ID → CLASSIFICATION_ID → PASSPORT_ID → RELATION_ID → CANON_ID`

Не каждый объект обязан иметь все последующие звенья.

### Уровни трассировки

1. **Referential trace** — OBJECT → SOURCE.
2. **Production trace** — OBJECT → предшествующие записи → SOURCE.
3. **Dependency-aware trace** — OBJECT ← конкретные основания.

Для критичных объектов должен сохраняться dependency-aware trace.

---

## 5. Статусы

### 5.1. Жизненный статус

`ЧЕРНОВИК → ПРОВЕРЕН → КАНОНИЗИРОВАН`

### 5.2. Эпистемический статус

`UNKNOWN / PROVISIONAL / NEEDS_EVIDENCE / CANONICAL`

Два измерения не смешиваются в одном поле.

---

## 6. Кандидат и объект

Переход:

`CANDIDATE → OBJECT`

не является автоматическим.

Он требует явного производственного решения и соответствующего статуса.

Обязательные различения:

- `TERM OCCURRENCE ≠ TERM ENTITY`;
- `SAME TERM ≠ SAME ENTITY`;
- `TYPE ≠ CANONICAL OBJECT`;
- `RELATION CANDIDATE ≠ ESTABLISHED RELATION`;
- `PASSPORT ≠ INVENTION`.

---

## 7. Неопределённость и отсутствие результата

Для каждого входного объекта должен быть зафиксирован один из результатов:

- создан выходной объект;
- `N/A` с причиной;
- `UNKNOWN`;
- `PROVISIONAL`;
- `NEEDS_EVIDENCE`;
- зарегистрирована производственная причина остановки.

Состояние «не обработан» без объяснения и статуса недопустимо.

### Потеря основания

Если удалено существенное основание, степень уверенности в производном объекте должна быть пересмотрена.

Допустимый переход, например:

`CANONICAL → PROVISIONAL → NEEDS_EVIDENCE`.

---

## 8. Семантические инварианты

Машина обязана удерживать как минимум:

- `SOURCE ≠ REPRESENTATION`;
- `ACTIVITY ≠ MANAGEMENT`;
- `FORMAL PROCESS ≠ MANAGEMENT ARCHITECTURE`;
- `ABSENCE OF EVIDENCE ≠ EVIDENCE`.

Эти различения являются ограничениями производства, а не содержанием конкретного Источника.

---

## 9. Handoff и возврат

Нормальный переход:

`OUTPUT[n] → INPUT[n+1]`

Следующий модуль не обязан перечитывать SOURCE, если входной Batch содержит необходимую трассировку.

Возврат к SOURCE допускается при:

- споре;
- обнаруженной ошибке;
- необходимости уточнения;
- аудите;
- дефиците основания;
- появлении нового материала Источника.

Возврат не даёт права молча переписывать предыдущий Batch.

## 11. Контроль качества

Минимальные QC-gates:

1. SOURCE INTEGRITY.
2. TRACEABILITY.
3. HANDOFF.
4. SEMANTIC SEPARATION.
5. REVERSE TRACE.
6. NEGATIVE TEST.
7. **DECISION RULE CONSISTENCY** — одинаковая процедура принятия решения при одинаковом основании.

---

## 12. Обязательные тесты

### Test A — Handoff

Результат каждого модуля используется как вход следующего.

### Test B — Full lineage

Проверяется цепочка от результата до SOURCE.

### Test C — Negative evidence

Удаление существенного основания должно приводить к пересмотру уверенности.

### Test D — Same-term

Одинаковое написание термина не должно автоматически создавать одну сущность.

### Test E — Repeatability

Один и тот же SOURCE и одинаковый контракт должны давать сопоставимую структуру результата.

### Test F — Automated execution

Production M01–M08 выполняются программным агентом через формальные TASK-интерфейсы.

Контроль считается пройденным, если:

1. каждый TASK получает допустимый INPUT по своему контракту;
2. создаётся отдельный BATCH;
3. фактический OUTPUT предыдущего TASK передаётся следующему через HANDOFF;
4. HANDOFF проходит контрактную проверку;
5. промежуточные семантические результаты не конструируются вручную;
6. SOURCE_ID и traceability сохраняются;
7. исключения и отрицательные ветви не превращаются в скрытые положительные результаты.

AUTOMATED RUN является отдельным типом доказательства и не заменяет проверки семантических и relation-dependent ветвей.

## 13. M08 — DECISION RULE

M08 принимает source-bound решение о степени основания объекта.

Последовательность:

**1. Source Evidence**

Есть ли прямое основание в SOURCE для утверждаемого объекта?

- NO → `NEEDS_EVIDENCE` + `EVIDENCE_GAP`.
- YES → следующий тест.

**2. Object Boundary**

Однозначно ли определена граница одного объекта на основании SOURCE и PASSPORT?

- NO → `NEEDS_EVIDENCE` + `EVIDENCE_GAP`.
- YES → следующий тест.

**3. Type Assignment**

Подтверждается ли назначенный класс объекта SOURCE и PASSPORT без привлечения внешнего основания?

- NO → `NEEDS_EVIDENCE` + `EVIDENCE_GAP`.
- YES → `PROVISIONAL`.

**4. Canonical**

`CANONICAL` не присваивается только потому, что один SOURCE прямо поддерживает объект.

Канонический статус требует отдельного CMOC-критерия канонизации.

### Обязательное поле

Каждый `NEEDS_EVIDENCE` обязан содержать конкретный:

`EVIDENCE_GAP`

Он должен отвечать на вопрос:

> Что именно не установлено и какое дополнительное основание требуется?

### Запрещённые основания для NEEDS_EVIDENCE

Само по себе не является основанием:

- необычность типа;
- сложность объекта;
- незнакомость термина;
- принадлежность к GUIDANCE;
- наличие SOURCE_IDENTITY;
- отсутствие канонизации;
- желание доказать универсальность объекта за пределами SOURCE.

## 14. Третий контрольный прогон M08

Третий прогон не является обязательным элементом каждого повторного теста.

Он запускается только при наличии проверяемой гипотезы о дефекте или неоднозначности DECISION RULE.

### Третий прогон НУЖЕН, если:

1. одно и то же основание допускает разные решения по правилу;
2. формулировка критерия допускает несколько операционных трактовок;
3. для разных классов объектов правило требует разных незафиксированных процедур;
4. оставшиеся EVIDENCE_GAP невозможно одинаково интерпретировать по формализованной процедуре.

### Третий прогон НЕ НУЖЕН, если QC подтверждает:

- полноту входов и решений;
- обязательность EVIDENCE_GAP;
- однозначную последовательность критериев;
- независимость решения от имени и порядка объекта;
- отсутствие скрытого unresolved gap под PROVISIONAL;
- воспроизводимость решения по фиксированной процедуре.

Принцип:

> Третий прогон нужен не для увеличения количества прогонов, а для проверки конкретной гипотезы, которую нельзя проверить уже выполненным контролем.

## 21. TASK interchangeability

`TASK` является самостоятельным параметром производственного интерфейса. На одном `SOURCE_PACKAGE` SRC-003 проверены `EXTRACTION`, `DISTINCTIONS` и `FORMULATIONS` напрямую от SOURCE_PACKAGE при неизменном ядре MACHINE-SOURCE-001.

В пределах проведённых тестов сменяемость `SOURCE_PACKAGE` и сменяемость `TASK` являются независимыми измерениями интерфейса машины.

## 22. Прямой вход TASK

Проведён отдельный тест `TASK=FORMULATIONS` непосредственно от `SOURCE_PACKAGE`, без использования предыдущего M03.

Результат: `SOURCE → 20 source observations → 60 FORM`.

Проверено: 20 входов; 60 формулировок; 3 уровня на вход; предыдущий M03 не использован; traceability to SOURCE PASS; external knowledge NONE; downstream fields NONE.

Это устанавливает, что предыдущий проход не является технически обязательным входом для каждого TASK. Допустимая точка входа определяется контрактом TASK.

## 29. Relation-dependent ветвь

M07/M08 relation-dependent branch испытана отдельно. Изолированный Passport даёт явный `NO_RELATION`; source-supported multi-object context позволяет создать relation candidates и передать их в M08. CANONICAL автоматически не присваивается.

### Automated negative branch

В рамках текущего production automated run проверена отрицательная ветвь relation-dependent M07/M08 без предоставленного relation evidence.

Фактическая последовательность:

`M06 PASSPORTS → M07 → NO_RELATION → HANDOFF → M08 → 0 DECISION_RECORDS`

M07 не сформировал relation candidate при отсутствии source-bound relation evidence.

Фактический результат:

- M07: `NO_RELATION`;
- `basis_refs = []`;
- `relation_evidence = []`;
- M08: `DECISION_RECORDS` с `records = []`.

Данный результат подтверждает, что отсутствие relation evidence не преобразуется M08 в установленное отношение или downstream decision.

Положительная relation-evidence ветвь подтверждена отдельным controlled evidence и не считается повторно доказанной данным AUTOMATED RUN.

## 30. Следующая операция

Базовый production AUTOMATED RUN M01–M08 на SRC-002 выполнен и принят в пределах контролируемой NO_RELATION ветви.

Подтверждено:

`SOURCE_PACKAGE → M01 → M02 → M03 → M04 → M05 → M06 → M07 → M08`

через production BATCH и формальные HANDOFF без ручного конструирования промежуточных семантических результатов.

Следующий производственный этап:

1. проверка воспроизводимости технологии на новом SOURCE;
2. проверка сохранения контрактов и traceability при смене SOURCE;
3. отдельное расширение automated relation branch при наличии соответствующего source-bound evidence.

Следующий этап не должен расширять доказательство за пределы фактически проверенных условий.

Не установлено данным AUTOMATED RUN:

- distributed execution;
- process isolation;
- failure recovery между независимыми машинами;
- семантическая полнота;
- автоматическая канонизация;
- автоматическое обнаружение положительных relations на произвольном SOURCE.
