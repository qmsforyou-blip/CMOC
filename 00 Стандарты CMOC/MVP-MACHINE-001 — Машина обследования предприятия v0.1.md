# MVP-MACHINE-001 — Машина обследования предприятия v0.1

**Дата:** 18-09-2026  
**Статус:** CANDIDATE  
**Основание:** «Программа обследования предприятия», lines 1–186.

---

## 1. Назначение

Определить фактическое состояние системы управления предприятия.

Выходы, прямо заданные Источником:

- перечень процессов;
- перечень внутренних продуктов;
- предварительные границы ответственности;
- перечень организационных разрывов;
- перечень специальных процессов;
- архитектурное заключение;
- предложения по развитию.

---

## 2. Вход

Источник задаёт следующие виды материала для обследования:

- интервью;
- документы;
- производство;
- лаборатория;
- взаимодействие подразделений.

Полный состав входных данных, их формат и критерии достаточности Источником не определены.

**Статус:** NEEDS_EVIDENCE.

---

## 3. Производственная операция

Выполнить:

1. интервью;
2. анализ документов;
3. анализ производства;
4. анализ лаборатории;
5. анализ взаимодействия подразделений;
6. согласование результатов.

Язык результата — организационная инженерия.

Стиль фиксации результата:

- императив;
- минимум слов;
- максимум смысла;
- без лишнего связующего текста.

---

## 4. Выход

Минимальный комплект результата:

`PROCESSES`

`INTERNAL_PRODUCTS`

`RESPONSIBILITY_BOUNDARIES`

`ORGANIZATIONAL_GAPS`

`SPECIAL_PROCESSES`

`ARCHITECTURAL_CONCLUSION`

`DEVELOPMENT_PROPOSALS`

---

## 5. Минимальный паспорт машинки

**MACHINE_ID:** MVP-MACHINE-001

**Название:** Машина обследования предприятия

**Цель:** получить фактическую картину системы управления и подготовить архитектурную основу проекта.

**INPUT:** данные обследования предприятия.

**OPERATION:** обследование + фиксация + согласование результатов.

**OUTPUT:** 7 блоков результата.

**CUSTOMER:** следующий этап консалтингового проекта.

---

## 6. Что уже можно использовать

Эта версия годится как **рабочий каркас**, а не как завершённая методика.

Можно провести первое обследование по семи выходам, используя пять заявленных областей обследования.

При этом не следует пока придумывать:

- состав вопросов интервью;
- форму протокола;
- критерии полноты обследования;
- алгоритм выявления разрывов;
- правила построения границ ответственности;
- критерии архитектурного заключения;
- критерии качества предложений.

Эти элементы требуют отдельного основания или проектирования.

---

## 7. Связь с CMOC

Машина имеет форму:

`INPUT → OPERATION → OUTPUT`

Но пока не имеет полного формального TASK CONTRACT.

Следовательно:

**Статус машины: CANDIDATE.**

Следующий полезный шаг — не расширять описание машины, а выполнить один реальный проход на собственном консалтинговом объекте и по его результатам обнаружить недостающие контракты.

---

## 8. MVP-принцип

Не строить идеальную машину заранее.

Сначала:

`REAL CASE → RUN → OUTPUT → QC → MACHINE REVISION`

Каждый обнаруженный пробел фиксировать как отдельное изменение.

---

## 9. Трассировка

`SOURCE: Программа обследования предприятия`

→ `MVP-MACHINE-001`

→ конкретный RUN

→ 7 выходных блоков.

Текущая версия не содержит доказательства реального запуска.

**Evidence status:** SOURCE-SUPPORTED / NOT YET RUN.

---

## 10. Критерий следующего запуска

Машина считается практически испытанной после одного полного реального прохода, если:

- все 7 выходов созданы;
- каждый выход имеет основание;
- отсутствующие основания отмечены;
- результаты согласованы;
- весь проход имеет собственный BATCH_ID;
- результат можно восстановить без скрытого контекста чата.
