# ARCH-001 — Архитектурный стек параметризованной производственной машины

**Версия:** v0.1  
**Дата:** 18-09-2026  
**Статус:** Working Architectural Record  
**Основание:** INV-001 + STD-007 + SPEC-002 + PROMPT-001 + TASK-CONTRACT-001 v0.2 + CONTROL-RUN-007…011

---

## 1. Назначение

Зафиксировать архитектурную структуру, обнаруженную при испытаниях AGENT-SOURCE-001 / MACHINE-SOURCE-001.

Документ не создаёт новую производственную семантику. Он связывает уже существующие инвариант, стандарты, контракты и контрольные прогоны в одну архитектурную схему.

---

## 2. Архитектурная формула

`INVARIANT → MACHINE → TASK CONTRACT → SOURCE PACKAGE → BATCH → OUTPUT → HANDOFF`

В развёрнутом виде:

`INV-001`
→ задаёт архитектурное ограничение  
→ `STD-008 MACHINE-SOURCE-001` реализует фиксированное ядро машины  
→ `TASK-CONTRACT-001` определяет допустимую производственную операцию и вход  
→ `STD-007 / SPEC-002` задают сменный SOURCE_PACKAGE  
→ `BATCH` фиксирует конкретный запуск  
→ `OUTPUT` является явным результатом операции  
→ `HANDOFF` передаёт результат следующей операции.

---

## 3. Слои

| Слой | Артефакт | Что фиксирует |
|---|---|---|
| INVARIANT | INV-001 | `MACHINE ≠ SOURCE ≠ TASK ≠ BATCH` |
| MACHINE | STD-008 | фиксированное производственное ядро |
| SOURCE INTERFACE | STD-007 / SPEC-002 | сменный материал Источника |
| WORKING INSTRUCTION | PROMPT-001 | исполняемую инструкцию машины |
| TASK CONTRACT | TASK-CONTRACT-001 | допустимый вход, операцию и выход TASK |
| EXECUTION IDENTITY | BATCH_ID | конкретный проход |
| OUTPUT | результаты TASK | явный продукт операции |
| HANDOFF | контракт передачи | явный вход следующего TASK |
| QC / EVIDENCE | контрольные прогоны | проверка соблюдения архитектуры |

---

## 4. Что является фиксированным

Фиксированным является производственное ядро MACHINE:

- правила операции;
- обязательные поля;
- трассировка;
- статусы;
- критерии завершения;
- запреты;
- QC-gates;
- правила возврата;
- правила явной передачи результата.

SOURCE не встраивается в ядро MACHINE.

TASK не встраивается в SOURCE.

Предыдущий результат не становится скрытым состоянием MACHINE.

---

## 5. Что является параметрами

### SOURCE

`SOURCE_PACKAGE` — материал конкретного Источника.

Один логический SOURCE может состоять из нескольких взаимодополняющих файлов.

### TASK

`TASK` — явная производственная операция.

Один SOURCE_PACKAGE может использоваться несколькими TASK.

### BATCH

`BATCH_ID` — идентичность конкретного выполнения:

`SOURCE + TASK + конкретный проход`.

Каждый новый TASK/проход получает собственный BATCH_ID.

---

## 6. Handoff

Нормальная цепочка:

`OUTPUT₁ + declared HANDOFF → INPUT₂ → BATCH₂ → OUTPUT₂`

Следующий TASK получает результат предыдущего только через явно объявленный интерфейс.

Следствие:

> Суперагент может оркестрировать цепочку, не являясь скрытым хранилищем промежуточного знания.

---

## 7. Evidence boundary

Контрольными прогонами подтверждено:

1. фиксированное ядро сохраняется при смене SOURCE;
2. фиксированное ядро сохраняется при смене TASK в пределах проверенной области;
3. один SOURCE_PACKAGE может использоваться несколькими TASK;
4. M01–M03 имеют подтверждённый прямой вход SOURCE_PACKAGE;
5. каждый проход имеет отдельный BATCH;
6. промежуточный OUTPUT может стать INPUT следующего TASK через явный HANDOFF;
7. скрытая зависимость от предыдущего результата в проверенной цепочке M01→M02→M03 не обнаружена;
8. трассировка является частью производственного результата.

Основание: CONTROL-RUN-007, -008, -009, -010, -011.

---

## 8. Что пока не следует считать доказанным

Не установлено:

- что любой TASK может напрямую принимать SOURCE_PACKAGE;
- что любой TASK применим к любому SOURCE_PACKAGE;
- что одинаковая архитектурная схема гарантирует одинаковую содержательную полноту;
- что машина автоматически производит канонические объекты;
- что отсутствие скрытого состояния доказано для любой возможной реализации;
- что вся цепочка M01–M08 доказана именно как полностью автоматизированная система без дополнительных контрольных условий.

---

## 9. Архитектурное различение

Критически важно не смешивать четыре сущности:

`MACHINE` — **как производим**  
`SOURCE` — **из чего производим**  
`TASK` — **что производим сейчас**  
`BATCH` — **какой конкретно проход выполняем**

Это различение превращает «суперагента» из большого промпта в оркестратор независимых производственных операций.

---

## 10. Минимальная исполняемая модель

`INPUT + TASK + CONTRACT → BATCH → OUTPUT + TRACEABILITY`

Для цепочки:

`SOURCE_PACKAGE → TASK₁ → BATCH₁ → OUTPUT₁`

`OUTPUT₁ + HANDOFF → TASK₂ → BATCH₂ → OUTPUT₂`

`OUTPUT₂ + HANDOFF → TASK₃ → BATCH₃ → OUTPUT₃`

---

## 11. Архитектурный статус

**SUPPORTED BY CONTROL RUNS**, но в пределах явно указанной evidence boundary.

Документ является архитектурной фиксацией уже полученного результата, а не доказательством новых свойств системы.
