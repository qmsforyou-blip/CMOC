# R2.2 — NEW DECISION Evidence Model

**ID:** R2.2-NEW-DECISION-EVIDENCE-001  
**Дата:** 20-09-2026  
**Статус:** DESIGN / ARCHITECTURE CANDIDATE  
**Область:** NEW DECISION  
**Основание:** R2-NEW-CRITERIA-001 + R2.1-NEW-DECISION-BOUNDARY-001 + R1 Evidence

## 1. Цель

Определить минимальную evidence model, которая может быть передана отдельному слою **NEW DECISION** для решения:

> достаточно ли оснований допустить source-bound кандидата как новый объект CMOC?

R2.2 не вводит runtime NEW, не изменяет `reconciliation.py`, QUERY, OBJECT INDEX или CMOC.

## 2. Основная идея

NEW DECISION не должен получать только:

```
value
```

Он должен получать **доказательный пакет решения**:

```
CANDIDATE
+
RECONCILIATION EVIDENCE
+
QUERY EVIDENCE
+
BOUNDARY
+
TARGET TYPE
+
TRACEABILITY
```

## 3. Минимальная модель

Предлагаемая концептуальная структура:

```yaml
new_decision_input:
  candidate:
    record_id:
    value:
    object_boundary:

  reconciliation:
    match_result:
    basis:
    cmoc_object_id:

  query_evidence:
    query_scope:
    modes:
      exact:
      alias:
      structural:
    results:

  target_object_type:

  traceability:

  decision_context:
```

Это **design model**, а не действующий контракт.

## 4. Candidate

Candidate должен происходить непосредственно из source-bound Discovery lineage.

Минимум:

```
record_id
value
object_boundary
```

При этом:

- `record_id` адресует исходную запись;
- `value` передаётся без семантического обогащения;
- `object_boundary` определяет, что именно предлагается считать одним кандидатом.

NEW DECISION не должен сам восстанавливать boundary из внешнего знания.

## 5. Reconciliation Evidence

NEW DECISION должен видеть фактический результат предыдущего слоя:

```
match_result
basis
cmoc_object_id
```

Для текущей ветки NEW ожидается:

```
match_result = NEEDS_REVIEW
```

и основание, подтверждающее отсутствие установленной эквивалентности.

Особенно:

```
NO_MATCH
→
NEEDS_REVIEW
```

не должно превращаться в NEW без дальнейшей проверки.

## 6. Query Evidence

Нужно сохранить не только итог `NO_MATCH`, но и **условия, при которых он был получен**.

Минимально:

```
query_scope
exact
alias
structural
```

Каждый режим должен позволять установить:

- выполнялся ли;
- какой был результат;
- на каком основании;
- не был ли результат ограничен scope.

### Важный принцип

```
NO_MATCH
```

без:

```
query_scope
+
mode history
```

не является достаточным evidence для NEW.

## 7. Evidence state

Для каждого evidence item предлагается использовать только явные состояния:

```
TRUE
FALSE
NOT_APPLICABLE
UNKNOWN
```

Не допускается:

```
UNKNOWN → TRUE
```

или:

```
missing → passed
```

Предлагаемый набор:

```yaml
evidence_state:
  source_bound_candidate: TRUE/FALSE/UNKNOWN
  traceability_complete: TRUE/FALSE/UNKNOWN
  query_scope_sufficient: TRUE/FALSE/UNKNOWN
  exact_checked: TRUE/FALSE/UNKNOWN
  alias_checked: TRUE/FALSE/NOT_APPLICABLE/UNKNOWN
  structural_checked: TRUE/FALSE/NOT_APPLICABLE/UNKNOWN
  no_ambiguity: TRUE/FALSE/UNKNOWN
  no_unresolved_candidate: TRUE/FALSE/UNKNOWN
  stable_object_boundary: TRUE/FALSE/UNKNOWN
  target_object_type_resolved: TRUE/FALSE/UNKNOWN
```

## 8. UNKNOWN как защитный режим

UNKNOWN означает:

> evidence отсутствует или его достаточность не установлена.

UNKNOWN не означает FALSE.

Но для автоматического APPROVE:

```
UNKNOWN
→
не достаточно оснований
```

То есть автоматическое решение должно быть monotonic в сторону безопасности:

```
не доказано
→
не APPROVE
```

## 9. Candidate states

До NEW DECISION полезно различать:

```
CANDIDATE
   ↓
ELIGIBLE_FOR_NEW_DECISION
   ↓
NEW_APPROVED / NEW_REJECTED
```

`ELIGIBLE_FOR_NEW_DECISION` не означает NEW.

Это только означает:

> пакет доказательств достаточно сформирован для принятия решения.

## 10. Предлагаемый decision gate

Концептуально:

```
NEW_DECISION_INPUT
       ↓
evidence validation
       ↓
┌─────────────────────────┐
│ all mandatory evidence  │
│ TRUE / valid N/A        │
└────────────┬────────────┘
             │ YES
             ↓
      ELIGIBLE_FOR_DECISION
             ↓
       NEW DECISION
        /        \
 APPROVED       REJECTED
```

Если обязательный evidence item = FALSE или UNKNOWN:

```
→ NOT_ELIGIBLE / NEEDS_REVIEW
```

## 11. target_object_type

R2.2 подтверждает ограничение R2.1:

```
working_class
      X
      ↓
target_object_type
```

Автоматическое отображение запрещено.

Для NEW DECISION target type должен быть:

1. явно заданным разрешённым входом; или
2. получен отдельным будущим mapping-контрактом.

Если target type не разрешён и не определён:

```
target_object_type_resolved = UNKNOWN
```

и автоматический APPROVE запрещён.

## 12. Object boundary

Boundary должен быть source-supported.

Минимально требуется понимать:

- какой candidate рассматривается;
- что входит в его границу;
- что не входит;
- на какой source evidence основана граница.

NEW DECISION не должен создавать boundary самостоятельно на основании semantic similarity.

## 13. Traceability

Decision evidence должен сохранять путь:

```
SOURCE
 ↓
SOURCE_PACKAGE
 ↓
DISCOVERY_RUN
 ↓
M06_BATCH
 ↓
PASSPORT
 ↓
RECONCILIATION_INPUT
 ↓
QUERY / RECONCILIATION
 ↓
NEW_DECISION
```

Каждый decision claim должен быть возвращаем к соответствующему upstream evidence.

## 14. Decision record

Если в будущем решение будет принято, минимальная форма результата:

```yaml
new_decision:
  decision_id:
  candidate_record_id:
  decision:
    APPROVED / REJECTED
  basis:
  evidence_refs:
  traceability:
  status:
```

Это design-only.

Наличие decision record ещё не означает CMOC WRITE.

## 15. Что NEW DECISION может утверждать

При APPROVED:

> В рамках определённого query scope и при выполнении заданных evidence criteria source-bound candidate допускается как кандидат на создание нового CMOC объекта.

Не утверждается автоматически:

- абсолютная новизна знания;
- истинность содержания источника;
- внешняя уникальность;
- каноничность;
- готовность к записи.

## 16. Что NEW DECISION не может утверждать

Не допускаются выводы:

```
NO_MATCH → "этого объекта нигде не существует"
```

или:

```
APPROVED → "объект уже канонизирован"
```

или:

```
APPROVED → "CMOC изменён"
```

## 17. Relation to CANONIZATION

После:

```
NEW_APPROVED
```

следует отдельная граница:

```
CANONIZATION
```

Она должна определить:

- canonical object representation;
- canonical object_id;
- required properties;
- allowed relations;
- physical representation.

Конкретные правила пока не определяются.

## 18. Relation to CMOC WRITE

Последовательность:

```
NEW_APPROVED
   ↓
CANONIZATION
   ↓
WRITE GATE
   ↓
CMOC
```

WRITE GATE остаётся отдельным контролируемым переходом.

## 19. Минимальный evidence package

Для будущего runtime рекомендуется:

```
NEW_DECISION_INPUT
├── candidate
├── reconciliation
├── query_evidence
├── evidence_state
├── object_boundary
├── target_object_type
├── traceability
└── decision_context
```

## 20. Negative controls

R2.2 должен будет проверить минимум:

### NC-01
NO_MATCH + incomplete scope → not eligible.

### NC-02
NO_MATCH + UNKNOWN target type → not eligible.

### NC-03
NO_MATCH + unresolved CANDIDATE → not eligible.

### NC-04
NO_MATCH + AMBIGUOUS evidence → not eligible.

### NC-05
All required evidence valid → eligible for decision, но не автоматически APPROVED без отдельного decision rule.

### NC-06
APPROVED → no CMOC write.

## 21. Critical distinction

R2.2 вводит три разных состояния:

```
NO_MATCH
   ↓
ELIGIBLE_FOR_NEW_DECISION
   ↓
NEW_APPROVED
```

Они не являются синонимами.

### NO_MATCH

Нет найденного соответствия.

### ELIGIBLE_FOR_NEW_DECISION

Доказательный пакет достаточно сформирован для принятия отдельного решения.

### NEW_APPROVED

Отдельный decision layer разрешил рассматривать кандидата как новый объект.

## 22. Следующий эксперимент

R2.3 может проверить минимальный evidence package на синтетических ветках:

1. полный пакет → ELIGIBLE;
2. missing scope → NOT_ELIGIBLE;
3. unknown target type → NOT_ELIGIBLE;
4. unresolved candidate → NOT_ELIGIBLE;
5. ambiguous → NOT_ELIGIBLE.

При этом ни одна ветка не должна писать в CMOC.

## 23. Статус

**DESIGN / ARCHITECTURE CANDIDATE**

Не является действующим контрактом.

Не изменяет:

- `reconciliation.py`;
- SPEC-005;
- RECONCILIATION-INPUT-CONTRACT-001;
- DISCOVERY-RESULT-CONTRACT-001;
- OBJECT INDEX;
- CMOC.

## 24. Рабочее правило R2.2

> **NEW DECISION принимает решение не по одному NO_MATCH, а по целостному доказательному пакету.**

И:

> **ELIGIBLE_FOR_NEW_DECISION ≠ NEW_APPROVED ≠ CMOC WRITE.**
