# R2 — Критерии перехода NO_MATCH → NEW

**ID:** R2-NEW-CRITERIA-001  
**Дата:** 20-09-2026  
**Статус:** DESIGN / ARCHITECTURE CANDIDATE  
**Область:** RECONCILIATION  
**Основание:** SPEC-005 v0.3, RECONCILIATION-INPUT-CONTRACT-001, DISCOVERY-RESULT-CONTRACT-001, R1 Evidence

## 1. Цель

Определить, какие условия должны быть выполнены, чтобы результат:

```
QUERY = NO_MATCH
```

мог быть рассмотрен как основание для:

```
RECONCILIATION = NEW
```

Документ не вводит реализацию NEW и не изменяет текущий `reconciliation.py`.

## 2. Главный принцип

> **NO_MATCH — необходимое условие для NEW, но недостаточное условие.**

NO_MATCH означает только отсутствие найденного индексированного представления в проверенном query scope и при заданных query modes.

Поэтому:

```
NO_MATCH
   ≠
NEW
```

Это прямо следует из SPEC-005: неполный поиск не является доказательством отсутствия объекта.

## 3. Что должно быть доказано

Для перехода к NEW необходимо отдельно доказать две вещи:

### A. Достаточность поиска

Мы действительно проверили CMOC в области, которая имеет отношение к рассматриваемому source-bound кандидату.

### B. Достаточность идентичности кандидата

Мы понимаем, **что именно** хотим добавить как новый объект, а не просто имеем строку, которой не нашли.

Таким образом:

```
NEW =
SUFFICIENT_SEARCH
+
STABLE_CANDIDATE_IDENTITY
+
NO_EXISTING_MATCH
```

## 4. Критерий 1 — валидный source-bound candidate

До рассмотрения NEW должен существовать source-bound кандидат из DISCOVERY.

Минимально:

```
record_id
value
traceability
```

Кандидат должен иметь путь:

```
SOURCE
 → SOURCE_PACKAGE
 → DISCOVERY RUN
 → M06 PASSPORT
 → RECONCILIATION_INPUT
```

Discovery должен оставаться независимым от CMOC.

## 5. Критерий 2 — определена область поиска

`query_scope` должен быть явно задан.

Недопустимо:

```
NO_MATCH + неполный scope → NEW
```

Если QUERY возвращает:

```
SCOPE_INSUFFICIENT
```

переход к NEW запрещён.

Требование:

```
SCOPE_SUFFICIENT = TRUE
```

## 6. Критерий 3 — завершены разрешённые deterministic modes

Перед NEW должны быть завершены предусмотренные для данного кандидата режимы поиска.

Минимальная последовательность текущего MVP:

```
EXACT
  ↓
ALIAS
  ↓
STRUCTURAL (только если есть явно заданный structural_query)
```

Для NEW недостаточно:

```
EXACT = NO_MATCH
```

если ALIAS или разрешённый STRUCTURAL поиск ещё не выполнены.

## 7. Критерий 4 — отсутствует AMBIGUOUS

Если любой релевантный поиск дал:

```
AMBIGUOUS
```

NEW автоматически запрещён.

Причина:

```
AMBIGUOUS
=
существует несколько допустимых представлений,
но основание выбора отсутствует
```

Следовательно:

```
AMBIGUOUS → NEEDS_REVIEW
```

до отдельного разрешения неоднозначности.

## 8. Критерий 5 — отсутствует unresolved candidate

Если STRUCTURAL дал:

```
CANDIDATE
```

это означает, что найдено возможное соответствие.

Поэтому:

```
CANDIDATE → NEW
```

запрещено автоматически.

Сначала требуется отдельное разрешение candidate.

## 9. Критерий 6 — нет установленного existing equivalent

NEW не может быть сформирован, если какой-либо разрешённый режим поиска установил:

```
MATCH
```

Текущий R1 подтвердил:

```
MATCH → EXISTING_EQUIVALENT
```

NEW и EXISTING_EQUIVALENT являются взаимоисключающими результатами для одного decision context.

## 10. Критерий 7 — target object type

Для NEW необходимо понимать, **в какой класс CMOC должен попасть новый объект**.

Но текущий интерфейс специально запрещает автоматически делать:

```
working_class → target_object_type
```

Следовательно, при отсутствии отдельного mapping-контракта:

```
target_object_type = UNKNOWN
```

не должен превращаться в догадку.

Это означает:

> NEW нельзя автоматически считать доказанным только на основании отсутствия совпадения строки.

Нужен либо явно заданный target type, либо отдельное правило его определения.

## 11. Критерий 8 — стабильная граница нового объекта

Перед NEW должна быть определена граница source-bound кандидата:

```
object_boundary
```

Она должна отвечать на вопрос:

> Что именно предлагается добавить в CMOC как один объект?

Нельзя объявлять NEW на основании только:

```
value = "Fast Response"
```

если не определено, является ли это:

- TERM;
- DISTINCTION;
- GM_FORMULATION;
- MACHINE;
- PATTERN;
- CHAIN;
- LAW;
- другой допустимый объектный класс.

В текущем MVP это различение не выполняется автоматически.

## 12. Критерий 9 — отсутствие скрытого semantic enrichment

NEW не должен появляться потому, что система:

- придумала отсутствующий alias;
- вывела semantic similarity;
- восстановила отсутствующее имя;
- догадалась о target_object_type;
- извлекла смысл из текста вне разрешённых индексированных признаков.

Источник доказательства должен оставаться трассируемым.

## 13. Предлагаемый decision gate

Архитектурно переход можно представить так:

```
                    QUERY
                      ↓
                 NO_MATCH
                      ↓
             ┌─────────────────┐
             │ Scope sufficient│
             └────────┬────────┘
                      ↓ YES
             ┌─────────────────┐
             │ Modes completed │
             └────────┬────────┘
                      ↓ YES
             ┌─────────────────┐
             │ No ambiguity?   │
             └────────┬────────┘
                      ↓ YES
             ┌─────────────────┐
             │ No candidate?   │
             └────────┬────────┘
                      ↓ YES
             ┌─────────────────┐
             │ Identity stable │
             └────────┬────────┘
                      ↓ YES
             ┌─────────────────┐
             │ Target type      │
             │ resolved         │
             └────────┬────────┘
                      ↓ YES
                     NEW
```

Любое NO/UNKNOWN:

```
→ NEEDS_REVIEW
```

## 14. Важное различение

Нужно разделить два утверждения:

### Утверждение A

> «Мы не нашли существующий объект».

Это может быть доказано QUERY при достаточном scope.

### Утверждение B

> «Следовательно, это новый объект CMOC».

Это уже решение RECONCILIATION, а не результат QUERY.

QUERY может доказать A.

QUERY не может самостоятельно доказать B.

## 15. Что NEW НЕ означает

NEW не означает:

- объект гарантированно уникален во всём внешнем мире;
- объект никогда ранее не существовал;
- source является истинным или каноническим;
- semantic identity доказана вне заданного CMOC;
- объект автоматически готов к canonicalization.

NEW означает только:

> в заданной CMOC области поиска не установлено существующего соответствующего объекта, а source-bound кандидат удовлетворяет отдельным критериям допуска к созданию нового CMOC объекта.

## 16. Предлагаемый минимальный набор доказательств NEW

Для будущего контракта NEW рекомендуется зафиксировать:

```
NEW_EVIDENCE
├─ source_bound_candidate
├─ traceability_complete
├─ query_scope_sufficient
├─ exact_checked
├─ alias_checked
├─ structural_checked_or_not_applicable
├─ no_ambiguity
├─ no_unresolved_candidate
├─ stable_object_boundary
└─ target_object_type_resolved
```

Каждый элемент должен иметь явное значение:

```
TRUE / FALSE / NOT_APPLICABLE / UNKNOWN
```

UNKNOWN не должен автоматически трактоваться как TRUE.

## 17. Где должен находиться NEW

NEW не должен появляться в:

- QUERY;
- DISCOVERY;
- RECONCILIATION INPUT ADAPTER.

NEW относится к:

```
RECONCILIATION
```

или к отдельному downstream decision layer, если позднее будет принято такое разделение.

## 18. Текущая граница MVP

В текущем MVP нет достаточного контракта для автоматического NEW.

Поэтому текущая реализация правильно заканчивает ветку:

```
NO_MATCH
 → NEEDS_REVIEW
```

а не:

```
NO_MATCH
 → NEW
```

## 19. Следующий архитектурный вопрос

Перед написанием `NEW` необходимо решить:

> **Является ли NEW самостоятельным результатом RECONCILIATION или отдельным решением после RECONCILIATION?**

Это принципиальный вопрос границы.

Вариант A:

```
QUERY
 ↓
RECONCILIATION
 ↓
NEW
```

Вариант B:

```
QUERY
 ↓
RECONCILIATION
 ↓
NEEDS_REVIEW
 ↓
NEW DECISION
```

Данный документ не выбирает вариант.

## 21. Рабочее правило R2

> **NO_MATCH сообщает об отсутствии найденного соответствия. NEW требует дополнительного доказательства того, что кандидат допускается как новый объект CMOC.**

Это является рабочей гипотезой для следующего архитектурного обсуждения.
