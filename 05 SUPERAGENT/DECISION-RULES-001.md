# DECISION-RULES-001

## Статус
CONTRACT CANDIDATE — v0.1

## Назначение

Зафиксировать минимальные условия, при которых допустимы кандидатные решения после RECONCILIATION_RESULT.

Документ не выполняет Decision и не выполняет CMOC Admission.

## Общий принцип

Decision не заменяет Reconciliation и не повторяет его.

Decision использует результат Reconciliation и явно зафиксированное основание.

Никакое решение не должно возникать только из отсутствия совпадения.

## 1. ADMIT_EXISTING

### Допустимое основание

ADMIT_EXISTING может быть принято, если существует достаточное основание считать, что кандидат относится к уже существующему объекту CMOC.

Минимальная опора:

- существующий cmoc_object_id;
- ссылка на соответствующий результат Reconciliation;
- basis;
- traceability.

### Ограничение

EXISTING_EQUIVALENT из Reconciliation является сильным входом для ADMIT_EXISTING, но само по себе не является физическим admission.

Decision должен сохранять различие:

EXISTING_EQUIVALENT → ADMIT_EXISTING → ADMISSION

## 2. ADMIT_NEW

### Допустимое основание

ADMIT_NEW может быть принято только после явного рассмотрения кандидата и фиксации основания того, почему кандидат должен существовать как новый объект CMOC.

Минимальное отрицательное условие:

NO_MATCH сам по себе недостаточен.

NEEDS_REVIEW сам по себе недостаточен.

### Обязательное различение

Должно быть возможно ответить на вопрос:

> Почему этот кандидат является новым объектом, а не не найденным существующим объектом?

Ответ должен быть представлен в basis и traceability.

### Граница

ADMIT_NEW не создаёт объект CMOC автоматически в момент принятия Decision.

Физическое создание является отдельным ADMISSION шагом.

## 3. REJECT

### Допустимое основание

REJECT может быть принято, если явно зафиксировано основание, по которому кандидат не должен продолжать путь к CMOC Admission.

Basis обязателен.

### Ограничение

REJECT не должен использоваться как скрытый способ обозначить отсутствие данных для принятия решения.

Если оснований недостаточно, должен использоваться DEFER либо иной явно определённый статус.

## 4. DEFER

### Назначение

DEFER означает:

> окончательное решение на текущем проходе не принято.

Допустимые причины могут включать:

- недостаточность evidence;
- необходимость дополнительного рассмотрения;
- необходимость получения дополнительного контекста;
- необходимость эскалации.

Конкретная таксономия причин пока не утверждается.

### Ограничение

DEFER не является ADMIT_NEW, ADMIT_EXISTING или REJECT.

## 5. Минимальный Decision gate

До принятия любого решения должны быть известны:

1. конкретный match_id;
2. источник и lineage;
3. результат Reconciliation;
4. basis решения;
5. decided_by.

## 6. Запрещённые правила

Запрещены:

NO_MATCH → ADMIT_NEW

NEEDS_REVIEW → ADMIT_NEW без дополнительного основания

NEEDS_REVIEW → REJECT только потому, что автоматическое сопоставление не дало MATCH

EXISTING_EQUIVALENT → физическая запись в CMOC без отдельного ADMISSION

DECISION → CMOC write без отдельного ADMISSION шага

## 7. Что пока не определяется

Этот контракт не определяет:

- окончательную систему доказательств;
- полномочия человека и машины;
- автоматическое или ручное принятие конкретного решения;
- окончательную таксономию причин;
- физический механизм ADMISSION;
- правила изменения или отмены уже принятого Decision.

Это следующие архитектурные вопросы.

## 8. Минимальная цепочка

RECONCILIATION_RESULT
→ REVIEW / CONSIDERATION
→ DECISION
→ ADMISSION

REVIEW / CONSIDERATION не выделяется пока в отдельный RECORD.
