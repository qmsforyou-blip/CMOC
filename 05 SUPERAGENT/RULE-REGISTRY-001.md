# RULE-REGISTRY-001

## Статус
CONTRACT CANDIDATE — v0.1

## Назначение

Зафиксировать эксплуатационный реестр утверждённых правил, которые могут участвовать в автоматическом принятии DECISION.

## Архитектурная позиция

RULE Registry на текущем этапе является эксплуатационной инфраструктурой Decision.

RULE не становится автоматически объектом CMOC только потому, что используется runtime.

Связь:

APPROVED RULE
→ DECISION

не означает:

RULE
→ CMOC OBJECT

## Почему отдельный реестр нужен

После DECISION-AUTOMATION-001 система должна уметь однозначно установить:

- какое RULE применялось;
- какая версия RULE действовала;
- разрешено ли RULE к применению;
- к каким входам и решениям оно относится;
- кто его утвердил;
- действует ли оно сейчас.

Без этого APPROVED RULE не имеет проверяемой эксплуатационной идентичности.

## Минимальная запись RULE Registry

Каждая запись должна содержать:

- rule_id;
- version;
- name;
- status;
- scope;
- input_contract;
- conditions;
- decision_result;
- authority;
- approved_by;
- approved_at;
- effective_from;
- effective_to, если применимо;
- traceability;
- deterministic: true/false.

## Минимальные статусы

Кандидатная таксономия:

- DRAFT;
- APPROVED;
- ACTIVE;
- SUSPENDED;
- RETIRED.

Окончательная lifecycle-модель пока не утверждается.

## Требование к автоматическому Decision

Автоматический Decision может ссылаться только на RULE, которое:

- идентифицировано;
- имеет конкретную версию;
- имеет разрешённый статус;
- находится в своей области применимости;
- является детерминированным;
- не требует скрытого semantic inference.

## Версионирование

Decision должен сохранять не только rule_id, но и конкретную version.

Изменение RULE создаёт новую версию и не должно ретроактивно изменять уже принятые Decision.

## Authority

RULE Registry должен сохранять сведения о том:

- кто утвердил RULE;
- когда;
- в каком статусе;
- для какой области применения.

## Runtime boundary

RULE Registry не:

- выполняет Reconciliation;
- изменяет Discovery;
- изменяет RECONCILIATION_RESULT;
- принимает решение сам по себе;
- выполняет CMOC admission.

Runtime только получает утверждённое RULE и применяет его в пределах контракта.

## CMOC boundary

На текущем этапе:

- rule_registry_write — эксплуатационная операция;
- cmoc_write = NONE;
- object_index_write = NONE.

Не утверждается, что RULE никогда не станет CMOC-объектом. Это отдельный будущий архитектурный вопрос.

## Минимальная цепочка

RULE Registry
→ APPROVED RULE
→ Decision Authority
→ DECISION
→ ADMISSION

## Открытые вопросы

1. Где физически хранить RULE Registry?
2. Кто имеет право менять его статус?
3. Нужен ли отдельный approval workflow?
4. Какие RULE допускаются к ACTIVE?
5. Нужен ли автоматический проверяющий механизм для условий RULE?
6. Может ли RULE позднее быть канонизировано как объект CMOC?

До ответа на эти вопросы RULE Registry остаётся контрактом эксплуатационной инфраструктуры, а не реализованным runtime-компонентом.
