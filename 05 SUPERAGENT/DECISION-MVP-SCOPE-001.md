# DECISION-MVP-SCOPE-001

## Статус
CONTRACT CANDIDATE — v0.1

## Назначение

Определить минимальный объём Decision / Rule Governance, необходимый для текущего MVP, чтобы не строить преждевременную инфраструктуру автоматизации.

## Главный вывод

Полный RULE Governance для текущего MVP не требуется.

Текущий MVP должен поддерживать:

1. RECONCILIATION_RESULT;
2. HUMAN DECISION;
3. явный basis;
4. traceability;
5. отдельный ADMISSION шаг.

RULE Registry и автоматический Decision остаются подготовленной архитектурной возможностью, но не обязательной частью первого рабочего контура.

## MVP-цепочка

SOURCE
→ DISCOVERY
→ RECONCILIATION
→ RECONCILIATION_RESULT
→ HUMAN DECISION
→ ADMISSION
→ CMOC

## Что обязательно

### 1. Human Decision

Человек может принять:

- ADMIT_EXISTING;
- ADMIT_NEW;
- REJECT;
- DEFER.

При этом Decision обязан ссылаться на конкретный match_id и сохранять basis и traceability.

### 2. Admission boundary

Decision не выполняет физическую запись в CMOC.

Отдельный Admission шаг остаётся обязательной границей.

### 3. История

Должна сохраняться история:

RECONCILIATION_RESULT
→ DECISION
→ ADMISSION

Это необходимо для воспроизводимости и последующего анализа.

## Что НЕ требуется для MVP

Не требуется реализовывать:

- полноценный RULE Registry;
- автоматический lifecycle DRAFT → APPROVED → ACTIVE;
- автоматический Decision engine;
- отдельный policy authority layer;
- LLM как самостоятельный субъект Decision;
- сложный approval workflow;
- автоматическую активацию версий RULE.

## Что сохраняем как архитектурный задел

Уже определённые контракты:

- DECISION-AUTHORITY-001;
- DECISION-AUTOMATION-001;
- RULE-REGISTRY-001;
- RULE-GOVERNANCE-001.

Они не требуют немедленной runtime-реализации.

## Критерий возврата к автоматизации

К RULE automation следует возвращаться только когда появится реальный повторяющийся класс решений, для которого одновременно выполняются условия:

1. решения повторяются;
2. основание решения стабильно;
3. условия формализуемы;
4. результат детерминирован;
5. ошибка автоматизации контролируема;
6. существует экономический или операционный эффект от автоматизации.

## Архитектурный принцип

Не строить инфраструктуру для гипотетической автоматизации.

Сначала получить реальные Human Decisions.

Затем выявить повторяющиеся классы решений.

Затем формализовать наиболее устойчивый класс в RULE.

Затем решить, нужна ли его автоматизация.

## Следствие

В текущем MVP Rule Governance является архитектурным заделом, а не обязательным runtime-слоем.

Decision остаётся рабочим следующим шагом после Reconciliation.

ADMISSION остаётся отдельной следующей границей.
