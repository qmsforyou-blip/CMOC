# P9.1 — RUNTIME PRODUCTION E2E INTEGRATION GATE

**Status:** ACCEPTED  
**Layer:** production runtime realization  
**Predecessor:** P1-P8 runtime components  
**Purpose:** bind the proven runtime components into one durable recovery-aware execution test.

## 1. Purpose

P9.1 is a runtime integration gate over already proven P1-P8 components.

It does not introduce a new semantic machine.

The gate verifies that:

`P1/P2 → P3 → P4/P5 → P6 → P7 → P8 → RUN COMPLETION`

can operate under one RUN_ID while preserving lineage, failed-attempt history, retry identity, idempotency and responsibility boundaries.

## 2. Required components

The test must use the actual runtime components:

- RuntimeStateStore;
- AttemptStore;
- RestartResumeController;
- TransactionStore;
- ProductionAdapterRegistry;
- ProductionCmocWriter;
- ProductionObjectIndexSynchronizer.

Controlled production adapter callables may stand in for semantic implementations because P6 does not itself implement R1-R10.

## 3. Recovery scenario

The gate injects a failure before the first C2/P7 persistence attempt.

Required sequence:

`ATTEMPT-1 → FAILED → RECOVERY → RETRY_REQUIRED → ATTEMPT-2 → P7 SUCCESS → P8 SUCCESS → RUN COMPLETED`

The first attempt must remain in AttemptStore and journal history.

## 4. Restart scenario

After the failure is durably persisted, a fresh RestartResumeController must inspect the RUN and return:

`RETRY_REQUIRED`

After completion, a fresh controller must return:

`ALREADY_COMPLETED`

## 5. Physical persistence

P7 uses an isolated real filesystem target.

P8 invokes the real deterministic OBJECT INDEX builder in `--check` mode and verifies an existing addressable object identity.

The test must explicitly distinguish these two physical boundaries; P8 must not pretend that it directly indexes the temporary P7 fixture.

## 6. Transaction/idempotency

P5 must guard the retry attempt around the persistence effect.

A repeated commit must not create a second authoritative effect.

P7 repeated write must return `ALREADY_PERSISTED`.

P8 repeated synchronization must remain idempotent.

## 7. Responsibility boundary

P9.1 must not:

- perform semantic NEW decisions;
- perform semantic comparison;
- canonize;
- mutate CMOC outside P7;
- mutate OBJECT INDEX outside P8;
- rewrite failed history;
- convert execution failure into semantic approval.

## 8. Acceptance

PASS requires:

1. one RUN_ID through the complete tested chain;
2. durable journal/state persistence;
3. explicit failed attempt;
4. RECOVERY → RETRY_REQUIRED;
5. new ATTEMPT_ID;
6. P5 commit protection;
7. P6 production adapter invocation;
8. P7 physical persistence;
9. P8 real deterministic index verification;
10. completed RUN protection;
11. idempotent P7/P8 repeat;
12. no responsibility leakage.

## 9. Limitation

This gate proves the tested single-host runtime integration only.

It does not establish distributed execution, multi-node HA, external database deployment, network failure semantics, throughput, or universal production readiness.
