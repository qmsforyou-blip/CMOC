# O0.1 — PRODUCTION DEPLOYMENT PROFILE

**Status:** DESIGN / ARCHITECTURE CANDIDATE  
**Parent:** O0 — Operationalization Architecture  
**Purpose:** define the declared production deployment profile before operational readiness work is treated as applicable.

## 1. Boundary

O0.1 does not implement infrastructure.

It defines the operational context against which O1-O9 will be evaluated.

The profile is the reference for deciding which P10 limitations are:

- REQUIRED;
- NOT_REQUIRED_BY_PROFILE;
- DEFERRED;
- UNKNOWN.

An operational capability must not be marked complete merely because it is technically possible.

## 2. Profile identity

Candidate fields:

`PROFILE_ID`  
`PROFILE_VERSION`  
`PROFILE_STATUS`  
`OWNER`  
`DECLARED_SCOPE`

Profile versions must be explicit. A readiness result is valid only against a declared profile version.

## 3. Deployment topology

The profile must declare:

- single host / multi-host;
- physical / virtual / containerized deployment;
- local / shared / external storage;
- network boundaries;
- trusted and untrusted zones;
- expected geographic/site distribution.

Unknown topology remains UNKNOWN.

## 4. Process model

Declare:

- single process / multiple processes;
- worker model;
- scheduler/orchestrator model;
- service dependencies;
- process supervision mechanism;
- restart policy;
- shutdown behavior.

The process model must preserve RUN identity and P1-P5 execution guarantees.

## 5. Persistence model

Declare:

- CMOC storage target;
- execution journal storage;
- persistent RUN/stage state storage;
- OBJECT INDEX location;
- temporary/work directories;
- storage durability assumptions;
- filesystem/database/object-storage boundary.

Canonical CMOC remains the authoritative persisted representation.

OBJECT INDEX remains a deterministic derived artifact.

## 6. Expected workload

Declare at minimum:

- typical source size;
- maximum expected source size;
- typical batch size;
- maximum batch size;
- expected RUNs per day;
- expected concurrent RUNs;
- expected retry frequency;
- expected CMOC write frequency;
- expected OBJECT INDEX rebuild frequency.

Unknown values remain UNKNOWN and cannot be converted into capacity claims.

## 7. Availability requirement

Declare:

- required service availability;
- permitted planned downtime;
- failure tolerance;
- maintenance window;
- whether HA is REQUIRED.

If HA is not required by the declared profile, O7 must not be treated as an implicit mandatory feature.

## 8. Recovery requirements

Declare:

- target RPO;
- target RTO;
- acceptable loss of transient state;
- required restart behavior;
- required restore behavior;
- whether host loss must be tolerated;
- whether storage loss must be tolerated.

These requirements determine the applicable O3/O7/O8 evidence.

## 9. Security boundary

Declare:

- operator population;
- service identities;
- authentication mechanism;
- authorization model;
- privileged operations;
- secret storage;
- source-data sensitivity;
- network access restrictions.

Security requirements are operational controls and must not be implemented through semantic reinterpretation.

## 10. Backup and restore target

Declare:

- what must be backed up;
- backup destination;
- backup frequency;
- retention;
- restore verification frequency;
- acceptable restore point;
- whether CMOC and execution history require independent recovery.

The profile must preserve the distinction:

`CMOC = canonical authority`

`OBJECT INDEX = deterministic derivative`.

## 11. Observability environment

Declare:

- logs destination;
- metrics destination;
- alerting channel;
- operator dashboard;
- retention;
- required health signals;
- required RUN/stage/recovery visibility.

Observability must expose runtime state without changing semantic results.

## 12. Deployment and upgrade model

Declare:

- deployment mechanism;
- configuration management;
- versioning;
- upgrade strategy;
- rollback strategy;
- migration requirements;
- maintenance ownership.

Upgrade must preserve CMOC semantic boundaries and execution lineage.

## 13. Multi-node and distributed behavior

Declare explicitly:

`MULTI_NODE = REQUIRED | NOT_REQUIRED | DEFERRED | UNKNOWN`

If REQUIRED, the profile must additionally specify:

- coordination mechanism;
- shared state;
- leader/worker model;
- locking;
- network partition behavior;
- failover;
- split-brain protection.

If NOT_REQUIRED, these are outside the current production readiness claim.

## 14. Capacity evidence policy

O5 must measure the declared workload rather than infer capacity from architecture.

A capacity claim requires:

`DECLARED_LOAD + TEST_CONDITIONS + MEASURED_RESULT + ACCEPTANCE_CRITERIA`.

No throughput or capacity claim may be derived solely from P1-P9 structural tests.

## 15. Operational readiness scope

O9 evaluates readiness only for the declared profile.

Therefore:

`READY(profile-v1)`

does not mean:

`READY(for every deployment)`.

Changing topology, workload, availability target, security boundary or recovery requirements creates a new profile version and may require a new readiness evaluation.

## 16. Profile completeness

Candidate profile states:

- `PROFILE_INCOMPLETE`;
- `PROFILE_DECLARED`;
- `PROFILE_BASELINE`;
- `PROFILE_SUPERSEDED`.

Minimum declaration gate:

- topology defined;
- process model defined;
- persistence model defined;
- workload bounds defined or explicitly marked UNKNOWN;
- availability requirement defined;
- recovery requirements defined;
- security boundary defined;
- backup target defined;
- observability environment defined;
- deployment/upgrade model defined;
- multi-node requirement explicitly classified.

## 17. What O0.1 does not decide

O0.1 does not:

- implement O1-O9;
- select technologies;
- claim HA;
- claim throughput;
- claim security readiness;
- claim DR readiness;
- modify CMOC;
- modify OBJECT INDEX;
- introduce semantic decisions.

Technology selection belongs to the corresponding operational work package after the profile is declared.
