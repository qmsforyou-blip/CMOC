# R2.1 — Граница ответственности NEW DECISION

**ID:** R2.1-NEW-DECISION-BOUNDARY-001  
**Дата:** 20-09-2026  
**Статус:** ARCHITECTURE CANDIDATE  
**Область:** RECONCILIATION / NEW DECISION / CMOC WRITE  
**Основание:** R1 Evidence + R2 NEW Criteria + действующие контракты

## 1. Цель

Определить архитектурную границу между:

1. установлением отсутствия существующего соответствия;
2. решением о допуске кандидата как нового объекта;
3. последующей канонизацией и записью в CMOC.

Документ не вводит новый runtime-код и не изменяет текущие контракты.

## 2. Исходная граница

R1 подтвердил:

```
MATCH      → EXISTING_EQUIVALENT
NO_MATCH   → NEEDS_REVIEW
CANDIDATE  → NEEDS_REVIEW
AMBIGUOUS  → NEEDS_REVIEW
```

R2 установил:

> NO_MATCH является необходимым, но недостаточным условием NEW.

Следовательно, между `NO_MATCH` и записью нового объекта существует отдельная область ответственности.

## 3. Две рассматриваемые архитектуры

### A — NEW внутри RECONCILIATION

```
DISCOVERY
   ↓
RECONCILIATION
   ↓
QUERY
   ↓
NO_MATCH
   ↓
NEW
```

В этой модели RECONCILIATION одновременно:

- устанавливает отношение кандидата к существующему CMOC;
- принимает решение о допуске нового объекта.

### B — отдельный NEW DECISION

```
DISCOVERY
   ↓
RECONCILIATION
   ↓
QUERY
   ↓
NO_MATCH
   ↓
NEEDS_REVIEW
   ↓
NEW DECISION
   ↓
NEW APPROVED / REJECTED
```

В этой модели функции разделены.

RECONCILIATION отвечает за сопоставление.

NEW DECISION отвечает за дополнительное решение о допуске нового объекта.

## 4. Третья граница — CMOC WRITE

Независимо от A/B предлагается не смешивать решение NEW с физической записью:

```
NEW DECISION
   ↓
NEW APPROVED
   ↓
CANONIZATION
   ↓
CMOC WRITE
```

Таким образом:

```
NEW ≠ WRITE
```

Сам факт решения NEW не должен автоматически означать изменение CMOC.

## 5. Функциональные вопросы слоёв

| Слой | Вопрос |
|---|---|
| DISCOVERY | Что добыто из SOURCE? |
| QUERY | Какие индексированные представления найдены? |
| RECONCILIATION | Есть ли уже соответствующий объект? |
| NEW DECISION | Достаточно ли доказательств для допуска нового объекта? |
| CANONIZATION | Как новый объект должен быть оформлен в CMOC? |
| CMOC WRITE | Как approved representation физически записывается? |

## 6. Почему эти вопросы нельзя объединять

### RECONCILIATION

Работает с уже существующим CMOC через read-only QUERY.

Его задача — установить отношение source-bound кандидата к накопленному знанию.

### NEW DECISION

Должен оценивать достаточность доказательств.

Минимальный набор R2:

```
source_bound_candidate
traceability_complete
query_scope_sufficient
exact_checked
alias_checked
structural_checked_or_NA
no_ambiguity
no_unresolved_candidate
stable_object_boundary
target_object_type_resolved
```

### CANONIZATION

Это уже преобразование source-bound кандидата в нормативное представление CMOC.

Оно не должно происходить внутри QUERY или RECONCILIATION.

### CMOC WRITE

Это физическая мутация CMOC.

Она должна иметь собственную точку контроля и собственную трассировку.

## 7. Важный инвариант

Недопустима цепочка:

```
NO_MATCH
   ↓
автоматическая запись в CMOC
```

Также недопустима:

```
NO_MATCH
   ↓
NEW
   ↓
автоматическая запись в CMOC
```

Без отдельного решения, канонизации и write-gate.

## 8. Предварительная рекомендуемая архитектурная форма

Документ НЕ принимает окончательное решение A/B, но фиксирует рабочую архитектурную гипотезу:

```
SOURCE
   ↓
DISCOVERY
   ↓
DISCOVERY_RESULT
   ↓
RECONCILIATION
   ↓
QUERY
   ├──────────────→ EXISTING_EQUIVALENT
   │
   └──────────────→ NEEDS_REVIEW
                         ↓
                   NEW DECISION
                         ↓
                 NEW APPROVED / REJECTED
                         ↓
                    CANONIZATION
                         ↓
                     CMOC WRITE
```

При этом `NEEDS_REVIEW` не означает только NEW. Он может быть разрешён и в другое downstream решение, если соответствующий контракт будет введён позднее.

## 9. Почему NEW пока не должен появляться в текущем reconciliation.py

Текущий `reconciliation.py` уже подтверждён R1.

Его безопасная граница:

```
MATCH → EXISTING_EQUIVALENT
всё недоказанное → NEEDS_REVIEW
```

Добавление NEW сейчас потребовало бы одновременно вводить:

- критерии достаточности;
- target type resolution;
- object boundary validation;
- decision evidence;
- approval semantics.

Это было бы не исправлением текущего слоя, а расширением его ответственности.

## 10. Отдельный decision context

Будущий NEW DECISION должен получать не только строку `value`.

Минимально ему потребуется контекст:

```
source_bound_candidate
+
reconciliation_result
+
query_evidence
+
traceability
+
object_boundary
+
target_object_type
```

При этом source-derived данные должны оставаться неизменяемыми.

## 11. NEW APPROVED ≠ CANONICAL OBJECT

Даже после положительного NEW DECISION объект ещё может находиться до канонизации.

Следовательно:

```
NEW APPROVED
   ≠
CANONICAL CMOC OBJECT
```

Это позволяет отдельно контролировать форму, идентификатор, свойства, отношения и физическое представление нового объекта.

## 12. CMOC WRITE как отдельный gate

Предлагаемая последовательность:

```
NEW DECISION
   ↓
APPROVED
   ↓
CANONIZATION
   ↓
WRITE GATE
   ↓
CMOC
```

WRITE GATE должен проверять как минимум:

- наличие approved decision;
- наличие canonical representation;
- наличие target object type;
- наличие traceability;
- отсутствие нарушения immutable source boundary;
- отсутствие конфликта с текущим CMOC.

Конкретный write-contract пока не определяется.

## 13. Что R2.1 уже устанавливает

Подтверждается архитектурное разделение:

```
DISCOVERY
≠
RECONCILIATION
≠
NEW DECISION
≠
CANONIZATION
≠
CMOC WRITE
```

Это является более сильным результатом, чем простое добавление статуса NEW.

## 14. Что R2.1 НЕ решает

Не решаются:

- окончательный выбор A или B;
- точный контракт NEW DECISION;
- алгоритм target_object_type resolution;
- критерии canonicalization;
- write-contract;
- автоматическая генерация нового object_id;
- разрешение конфликтов;
- RELATED;
- semantic similarity.

## 15. Следующий эксперимент

Следующим шагом целесообразно сделать не NEW runtime, а **R2.2 — NEW DECISION input/evidence model**.

Цель:

проверить, достаточно ли набора:

```
candidate
+
reconciliation
+
query evidence
+
boundary
+
target type
+
traceability
```

для отдельного решения NEW без изменения CMOC.

## 17. Рабочее правило

> **Сопоставление отвечает на вопрос «есть ли уже объект?». Решение NEW отвечает на вопрос «достаточно ли оснований допустить новый объект?». Канонизация отвечает на вопрос «как его оформить?». WRITE отвечает на вопрос «как физически изменить CMOC?».**
